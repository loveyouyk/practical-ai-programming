# 棕地项目需求遗漏与 Change 更新流程

> 目标：在开发过程中发现需求遗漏、范围变化或设计假设错误时，提供一套可执行的更新流程。  
> 核心原则：发现遗漏后，先更新 `spec change`，再继续开发；不要直接靠代码“先补上再说”。

---

## 1. 为什么需要这份流程

在项目研发中，经常会出现这种情况：

1. 开发中发现原需求少了一条；
2. 联调时发现前后端对同一个字段理解不一致；
3. 做导出时发现“按筛选条件导出”原来没有写进 spec；
4. 做表单时发现 RP 上有字段，但需求文档没写；
5. 做权限时发现旧系统有约束，但新需求没覆盖。

如果没有一套正式更新流程，团队通常会走向两个极端：

1. **直接改代码，不改 spec**
   - 后果：代码和文档脱节，后面无法验收

2. **不停重写整套文档**
   - 后果：流程停滞，开发效率失控

这份流程的目标，是在“严谨”与“可推进”之间找到平衡。

---

## 2. 发现遗漏后，先判断是哪一类变化

不是所有遗漏都一样。先分类，后处理。

## 2.1 新 requirement

原来的 spec 里完全没有这项能力。

例子：

- 项目管理模块原来只写了“新增、修改、列表、导出”
- 开发中发现还必须支持“查看详情”

这种属于新增 requirement。

## 2.2 requirement 细化

原来有 requirement，但描述不完整。

例子：

- 原来只写“导出项目列表”
- 联调中发现业务要求其实是“按当前筛选条件导出项目列表”

这种属于 requirement 细化。

## 2.3 设计变更

requirement 没变，但实现路径变了。

例子：

- 原来计划新建项目状态字典
- 开发中发现必须复用旧字典服务

这种属于 design 变更。

## 2.4 任务补充

spec 和 design 都基本正确，但 tasks 漏了。

例子：

- 忘记在 tasks 里补“旧链路回归验证”

这种属于 tasks 补充。

---

## 2.5 什么时候会触发变更回写

变更回写不只在"开发中"触发。Demo 实战碰撞验证发现，以下三个阶段都可能触发：

### 阶段一：审批阶段（最早）

TL 审批 OpenSpec 四件套时发现 design 与历史项目约定不一致（如字段翻译方式、默认分页大小等）。此时应直接修正 design，无需等到开发阶段再触发。

### 阶段二：开发阶段（最常见）

实现过程中发现 spec 遗漏 requirement、design 的接口与真实代码不一致、tasks 缺少验证项。

### 阶段三：联调/测试阶段

前后端联调时发现 spec 对某个场景的描述与实际行为不符。

**核心原则不变：** 无论在哪个阶段触发，都是"先更新 change，再继续推进"。

---

## 3. 发现遗漏后的标准动作

建议固定成下面 6 步。对 M 级需求，步骤可精简为 3 步（判断类型 → 更新文档 → 继续），不需要每次都走完整 6 步。

## 第一步：暂停继续实现

先暂停对应点上的继续扩展，不要直接一边改代码一边“顺手补”。

不是要停掉整个项目，而是要暂停那条受影响链路，先把变更判断清楚。

## 第二步：先做影响分析

先回答：

1. 这是 requirement、design，还是 tasks 的问题？
2. 它会影响前端、后端还是两边都影响？
3. 它是局部补充，还是会改变本次交付范围？
4. 它还属于当前 change 吗？

## 第三步：判断留在当前 change 还是拆新 change

### 应留在当前 change 的情况

1. 仍属于同一个业务能力；
2. 仍属于同一交付窗口；
3. 只是原需求遗漏或细化；
4. 变更不会把范围扩大成另一个独立模块。

### 应拆新 change 的情况

1. 已经超出当前能力边界；
2. 会明显推迟当前交付；
3. 是另一个独立需求；
4. 已经不适合作为当前 PR 的一部分。

## 第四步：更新 OpenSpec artifacts

根据变化类型更新：

1. 范围变化 -> `proposal.md`
2. requirement 变化 -> `spec.md`
3. 设计决策变化 -> `design.md`
4. 工作项变化 -> `tasks.md`

## 第五步：同步实施计划和验收矩阵

如果 artifacts 变了，下面两个必须同步：

1. `Superpowers` 实施计划
2. 功能验收矩阵

否则你后面就会出现“spec 更新了，但计划和验收标准没更新”的断层。

## 第六步：再继续实现

这时再回到编码和联调阶段。

---

## 4. 实战判断：什么时候应该补到当前 change

### 例子 A：留在当前 change

项目管理模块开发中，发现导出必须“按当前筛选条件导出”。

判断：

1. 仍是 `project-management` capability 的一部分；
2. 不构成新模块；
3. 属于 requirement 细化；
4. 应直接补回当前 change。

### 例子 B：不应留在当前 change

项目管理模块开发中，业务又提出“项目审批流”“项目操作日志中心”。

判断：

1. 已经超出当前模块 MVP；
2. 很可能会延长交付；
3. 更适合作为新 change 单独管理。

---

## 5. 最重要的更新顺序

不要乱顺序，推荐固定成：

1. 发现遗漏
2. 影响分析
3. 判断是否留在当前 change
4. 更新 OpenSpec（必要时包括 `proposal.md`）
5. 更新实施计划
6. 更新验收矩阵
7. 更新 PR 描述
8. 继续开发

---

## 6. 提示词模板

## 6.1 影响分析提示词

```text
我们在开发当前功能过程中发现一个遗漏需求，请先不要直接修改代码。

遗漏/新增需求如下：
- [在这里写具体内容]

请先分析：
1. 这属于新 requirement、requirement 细化、设计变更，还是任务补充；
2. 它会影响 proposal、spec、design、tasks 中的哪些部分；
3. 它会影响前端、后端、联调、测试、发布中的哪些环节；
4. 它是否仍然适合留在当前 change 中，还是应该拆成新 change。

输出要求：
1. 先给分类结论；
2. 再给影响面；
3. 再给建议动作；
4. 不要直接进入实现。
```

## 6.2 更新当前 change 的提示词

```text
请基于刚才的影响分析，把这个遗漏需求补充到当前 OpenSpec change 中。

要求：
1. 如果是 requirement 变化，更新 spec；
2. 如果是范围变化，更新 proposal；
3. 如果是实现路径变化，更新 design；
4. 如果是工作项变化，更新 tasks；
5. 明确指出这次补充新增了哪些 requirement、scenario 或 tasks；
6. 不要重写无关内容。
```

## 6.3 同步计划与验收矩阵提示词

```text
请基于刚更新后的 OpenSpec artifacts，重新评估当前实施计划和验收矩阵。

要求：
1. 标出原计划中受影响的任务；
2. 补充新增任务；
3. 调整测试与联调项；
4. 更新验收矩阵；
5. 明确哪些已完成工作需要回归验证。
```

## 6.4 PR 同步提示词

```text
请基于当前 change 的最新更新，重新整理 PR 描述。

要求：
1. 明确说明这次需求补充是什么；
2. 说明它为什么仍然留在当前 change 中；
3. 说明新增 requirement 对前端、后端、测试的影响；
4. 不夸大影响范围，不遗漏兼容性风险。
```

## 7. 项目管理模块案例

假设你在做“项目管理模块”时，开发到导出功能，才发现：

> 产品真实要求不是“导出全部项目”，而是“导出当前筛选结果”。

### 这时怎么判断

1. 这不是一个全新模块；
2. 它属于已有 `Export Project List` requirement 的细化；
3. 应该留在当前 `project-management` change；
4. 但必须回写 spec 和验收矩阵。

### 更新动作

1. 在 `spec.md` 中补充：
   - 导出按当前筛选条件生效场景
2. 在 `design.md` 中补充：
   - 导出参数如何复用列表查询条件
3. 在 `tasks.md` 中补充：
   - 导出筛选联调与验证任务
4. 在验收矩阵中更新：
   - `Export Project List` requirement 的 scenario 和证据要求

### 对应提示词

```text
我们在开发 `project-management` 模块过程中发现一个遗漏需求：导出不是导出全部项目，而是要按当前筛选条件导出。

请先不要直接修改代码，先分析：
1. 这属于 requirement 细化还是新 requirement；
2. 它是否留在当前 change 中；
3. 它会影响 spec、design、tasks、验收矩阵中的哪些部分。

分析完成后，再给出应更新的 artifacts 清单。
```

---

## 8. 如何知道“遗漏需求已经真正纳入流程”

你不能只看代码是否改了。  
真正纳入流程，至少要看这 5 个地方是否同步：

1. `proposal.md`
2. `spec.md`
3. `design.md`
4. `tasks.md`
5. 实施计划
6. 验收矩阵

如果只改了代码，那只是“实现补丁”，不是“流程闭环”。

---

## 9. 最终结论

需求变更在项目研发中是常态，不是例外。  
真正成熟的流程，不是要求“需求永远不变”，而是要求：

> 需求一旦变化，能够被及时识别、及时分类、及时回写、及时同步到实现和验收体系中。

一句话总结：

> 发现遗漏后，先更新 change，再继续开发；不要让代码跑在 spec 前面。
