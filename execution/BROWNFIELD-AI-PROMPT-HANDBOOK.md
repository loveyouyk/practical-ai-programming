# 棕地项目前后端升级改造 AI 提示词手册

> 适用场景：接手历史 `Java + Spring Boot`、`Vue / React` 项目，在不了解代码库的前提下，使用 `OpenSpec + Superpowers` 推进新增功能和升级改造
> 使用边界：这份手册提供“可复制提示词资产”，不替代治理分流、OpenSpec 正式评审、验收矩阵、交付模板和人工审批。

在复制任何提示词前，建议先补看：

- `core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`

如果你不确定当前环境能否直接执行 `/opsx-*` 或 Superpowers，请先补看：

- `execution/AI-WORKFLOW-TOOLING-PREREQUISITES.md`

---

## 1. 使用原则

棕地项目里的提示词，核心不是“把需求说清楚”，而是“把约束说清楚”。

提示词里必须显式包含：

1. 当前项目是历史项目，不是绿地项目；
2. 必须先理解现状，再做设计和实现；
3. 在当前 change 范围内，以 OpenSpec artifacts 作为唯一规格真相源；
4. 前后端都必须复用现有模式；
5. 必须考虑兼容性、回滚点和验证证据。

如果没有这些约束，AI 极易按新项目思路重做。

## 1.1 复制提示词前先补齐输入

在把任一提示词直接发给 AI 前，至少先准备下面这些输入中的已知部分：

1. 当前需求所属治理路径：`S-Low` / `M-Medium` / `L / High Risk`
2. 当前 change 名称，或是否还未进入正式 change
3. 已知页面 / 接口 / 表 / 字段 / 设计稿 / RP / 历史文档
4. 当前项目规则基线是否已存在、是否已加载
5. 已知的不确定项和待确认项

如果上述信息都缺失，不应直接进入设计、生成规格或实现提示词。

## 1.2 AI 输出边界

在提示词里，最好同时约束下面 4 件事：

1. 没有证据的链路、字段、页面行为必须标记为 `待确认`；
2. 占位 API 路径、请求/响应样例必须明确说明是草案，不得冒充真实现网契约；
3. RP 或设计稿只能帮助理解可见交互，不能单独证明业务语义正确；
4. “具备上线评审条件”必须来自测试、联调、验收矩阵和人工确认的组合，而不是 AI 单方判断。

## 1.3 提示词也要先分流

这份手册提供的是“棕地项目可复用提示词资产”，但不代表所有提示词都适合所有需求。  
在实际使用前，应先按：

- `core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`

判断当前需求属于：

1. `S-Low`
2. `M-Medium`
3. `L / High Risk`

建议使用口径：

1. `S-Low`：优先使用最小提示词，不默认进入完整 OpenSpec 和完整执行手册；
2. `M-Medium`：优先使用“最小探索 + 最小 OpenSpec + 快速审批”提示词；
3. `L / High Risk`：可完整使用本手册中的探索、OpenSpec、计划、开发、验证提示词。

## 2. 分流起手提示词

## 2.1 `S-Low` 起手提示词

```text
这是一个微小且低风险的棕地项目需求。请不要默认进入完整 OpenSpec 重流程。

要求：
1. 默认遵守当前项目规则基线；
2. 先判断是否涉及权限、租户、导出语义、旧接口契约、事务边界；
3. 如果命中上述任一高风险点，立即提示我升级到更重流程；
4. 如果未命中高风险点，请直接给出最小实现建议、最小验证动作和剩余风险说明；
5. 不要把当前需求当成新项目开发；
6. 即使是最小需求，也不得在没有最小验证记录的前提下直接宣称“完成”。
```

## 2.2 `M-Medium` 起手提示词

```text
这是一个 M 级棕地需求。请基于以下约束生成最小 OpenSpec change。

【已知约束】（从探索结果搬运，示例）
1. 统一返回体 Response<T>，不使用 ResponseEntity
2. 异常使用 ServiceException，不使用 @ControllerAdvice
3. 租户通过 TenantContext.getTenantId()
4. [继续补充从探索中发现的约束...]

【QUIRK 警告】（从探索结果搬运，示例）
1. SearchForm 重置不自动搜索
2. BaseTable 默认 pageSize=20
3. [继续补充从探索中发现的 QUIRK...]

【待确认项】
1. [从探索中发现的不确定项]
2. [...]

要求：
1. 生成 proposal、spec、design、tasks 草案；
2. spec 每个 requirement 至少包含 1 个正常场景 + 1 个异常/兼容场景；
3. design 中严禁包含与数据翻译约定不一致的字段（如后端翻译的 xxxName）；
4. design 末尾必须有 Pending Confirmations 节；
5. 生成后停下，等待人工审批；
6. 如果发现边界不清或风险超出预期，请明确建议升级到完整流程。

骨架参考：execution/M-MEDIUM-MINIMAL-OPENSPEC-EXAMPLE.md
```

> **衔接提示：** 上面的【已知约束】【QUIRK 警告】【待确认项】三段，需要从探索阶段（4.1 节）的输出中手动搬运过来。这是 M 级流程中最关键的衔接动作 —— 不要依赖 AI "记住"上一轮对话的内容。

## 2.3 `L / High Risk` 起手提示词

```text
这是一个高风险棕地需求。请按完整流程工作，而不是轻流程。

要求：
1. 先做现状探索；
2. 再形成完整 OpenSpec artifacts；
3. 再形成实施计划；
4. 再按多角色方式执行；
5. 全程保留兼容性、验证、验收和发布证据；
6. 对不确定项明确标记为待确认，不允许猜测。
```

## 3. 通用开场提示词

```text
我们现在处理的是一个历史项目中的功能新增/升级任务，不是新项目开发。请按棕地项目模式工作。

工作原则：
1. 先理解现有前后端实现、数据库结构、页面入口和兼容约束；
2. 不允许跳过现状调研直接开始设计或编码；
3. 使用 OpenSpec 形成正式 change，在当前范围内作为唯一规格真相源；
4. 再用 Superpowers 把任务拆成实施计划，并按多角色方式执行；
5. 所有新增和升级都必须覆盖兼容性、回滚点和验证证据；
6. 对不确定的历史逻辑，必须显式列出待确认问题，不允许猜测。

请先输出：
1. 现状理解框架；
2. 调研步骤；
3. 需要我补充的关键信息；
4. 再进入 OpenSpec 设计阶段。
```

## 4. 历史项目接手阶段提示词

## 4.1 总体勘探

```text
你现在扮演棕地项目的技术调研助手。请先不要设计新功能实现，也不要直接写代码。你的任务是帮助我理解一个历史项目中与当前需求相关的现状。

请重点输出：
1. 相关前端入口页面、组件、路由和 API 调用位置；
2. 相关后端 Controller、Service、Repository、数据库表；
3. 已有功能能力和缺口；
4. 兼容性风险和可能影响的旧链路；
5. 需要进一步向业务确认的问题。
6. 共享组件的非直觉行为（QUIRK），例如：重置按钮是否自动触发搜索、弹窗确认是否自动关闭、默认分页大小是多少、字典服务的 key 类型等；
7. 数据翻译/格式化约定：列表接口中的状态/类型等枚举字段，是后端翻译返回名称还是前端用字典本地翻译？日期格式化由谁做？

要求：
1. 优先基于现有代码和文档总结；
2. 不要假设这是绿地项目；
3. 对不确定内容明确标注“待确认”；
4. 每条关键结论至少附一个真实文件路径；
5. 至少给出一条调用链、依赖链或页面到接口链；
6. 输出按“前端 / 后端 / 数据 / QUIRK / 数据翻译约定 / 待确认问题”分组。
```

## 4.2 后端链路勘探

```text
请分析这个历史项目中与当前需求相关的后端链路，重点找出：
1. 真实对外接口；
2. 调用它们的 Service 和 Repository；
3. 相关数据库表和字段；
4. 已有校验、异常、权限、租户或审计逻辑；
5. 新增功能最可能复用的扩展点。

要求：
1. 先准确描述现状；
2. 不要直接给重构方案；
3. 标出兼容性风险和禁止直接改动的点；
4. 至少附一个真实 Controller/Service/Repository 路径作为证据。
```

## 4.3 前端链路勘探

```text
请分析这个历史项目中与当前需求相关的前端链路，重点找出：
1. 页面入口和路由；
2. 现有页面组件结构；
3. API 调用封装层；
4. 状态管理方式；
5. 表单校验、错误提示、权限控制等现有约定；
6. 新增功能最应该沿用的现有模式。

要求：
1. 先总结已有模式，不要创造新框架；
2. 明确哪些页面和组件可能受影响；
3. 对不确定的页面行为标记为待确认；
4. 至少附一个真实页面文件或 API 封装路径作为证据。
```

## 5. 需求澄清阶段提示词

## 5.1 业务澄清

```text
请围绕这个历史项目中的新增/升级需求，一次只问一个关键问题，帮助我收敛以下内容：
1. 业务目标；
2. 目标用户；
3. 旧功能痛点；
4. MVP 范围；
5. 必须兼容的旧行为；
6. 非功能约束；
7. 上线方式和回滚要求。

要求：
1. 优先问影响兼容性和范围边界的问题；
2. 不要提前进入数据库设计和代码实现；
3. 当信息足够时，输出需求摘要和待确认问题清单。
```

## 5.2 升级类需求澄清

```text
请帮助我澄清一个历史功能升级需求。重点问清：
1. 当前行为是什么；
2. 目标行为是什么；
3. 哪些行为必须保留；
4. 是否允许修改接口结构；
5. 是否需要灰度、迁移和回滚。

要求：
1. 一次只问一个问题；
2. 先问现状，再问目标，再问兼容性；
3. 最后输出“当前行为 / 目标行为 / 兼容要求 / 风险 / 待确认”。
```

## 6. OpenSpec 阶段提示词

## 6.1 生成变更背景

```text
我们现在处理的是棕地项目中的功能新增/升级，不是新项目。请在生成 OpenSpec change 前，先把以下内容整理成“现状与变更背景”：

1. 当前系统已有相关能力；
2. 当前前后端链路；
3. 当前数据库、接口、页面约束；
4. 本次改动的目标；
5. 必须兼容的旧行为；
6. 风险和回滚点。

输出要求：
1. 用企业项目评审口径表达；
2. 不要直接给实现代码；
3. 结果要能直接作为 proposal 和 design 的输入；
4. 对关键结论附真实证据路径。
```

## 6.2 新增功能 proposal

```text
请为棕地项目中的新增功能编写 OpenSpec proposal。

要求：
1. 说明当前系统缺少什么能力；
2. 说明该能力会复用哪些现有前后端链路；
3. 明确哪些旧页面、旧接口、旧数据模型会受到影响；
4. 明确兼容性边界和非目标；
5. 用“在现有系统上增量扩展”的口径写，不要写成新系统建设方案。
```

## 6.3 新增功能 spec

```text
请为棕地项目中的新增功能编写 OpenSpec spec。

要求：
1. 使用 ADDED Requirements；
2. 每个 requirement 都要考虑与现有系统的兼容性；
3. 至少补充 1-2 个兼容性场景；
4. 明确旧页面、旧接口在功能上线后不应被破坏；
5. requirement 同时覆盖前端体验和后端行为。
```

## 6.4 升级功能 delta spec

```text
请为历史项目中的功能升级编写 OpenSpec delta spec。

要求：
1. 优先使用 MODIFIED Requirements；
2. 写清当前行为与目标行为差异；
3. 明确旧接口、旧页面、旧数据结构的兼容要求；
4. 补充迁移场景、降级场景、回滚场景；
5. 不要把升级需求写成全量重做。
```

## 6.5 设计文档

```text
请为棕地项目中的功能新增/升级编写 OpenSpec design。

要求：
1. 先说明现有实现结构和限制；
2. 再说明本次改动打算复用哪些模块、替换哪些模块；
3. 明确前端页面、API 契约、数据结构的改动范围；
4. 至少补充请求/响应字段示例或字段级契约说明；
5. 若 API 路径仍是占位表达，明确标记后续由探索结果替换；
6. 明确兼容策略、灰度策略、回滚策略；
7. 明确测试和验证重点应放在哪些旧链路上。
```

## 6.6 tasks 拆解

```text
请基于 proposal、spec、design 生成 OpenSpec tasks。

要求：
1. 按历史项目调研、后端改造、前端改造、联调、验证、发布准备分组；
2. 每个任务都要体现兼容性和回滚考虑；
3. 任务描述要适合后续用 writing-plans 继续展开；
4. 不要把任务写成抽象口号。
```

## 7. Superpowers 阶段提示词

## 7.1 writing-plans

```text
请基于当前 OpenSpec change 的 proposal、spec、design、tasks 生成实施计划。

要求：
1. 这是棕地项目，不是新项目；
2. 计划必须先处理调研与兼容性，再处理后端、前端、联调；
3. 每个任务要写清涉及的既有模块和受影响旧链路；
4. 每个任务要写清验证方式和需要保留的证据；
5. 如果计划与 OpenSpec artifacts 冲突，以 OpenSpec 为准，并先回写再重生计划；
6. 后续执行将使用 subagent-driven-development。
```

## 7.2 多角色执行

```text
请按 subagent-driven-development 执行这个棕地项目变更。

要求：
1. 每个任务开始前，先说明当前任务会复用哪些旧模块、影响哪些旧链路；
2. 每个任务完成后，先做 spec review，再做 code quality review；
3. review 时必须检查兼容性，而不只是检查新功能；
4. 没有明确验证结果，不要进入下一个任务；
5. 若发现历史实现与 spec 假设不一致，暂停并回到 OpenSpec 更新 artifacts；
6. 若字段契约、错误语义或接口路径与 design 不一致，也按同样规则先回写再继续。
```

## 7.3 请求代码审查

```text
请对当前棕地项目改动做代码审查。

检查重点：
1. 是否遵循现有项目模式；
2. 是否引入了无关重构；
3. 是否破坏旧页面、旧接口或共享组件；
4. 是否存在兼容性遗漏；
5. 是否有足够验证证据支持当前变更。
```

## 8. 后端实现提示词

```text
你现在在一个历史 Java 项目中新增/升级某个能力。请严格遵守现有项目规范，而不是按通用 Spring Boot 样板生成代码。

已知约束：
1. 必须遵循当前项目已有的 Controller / Service / Repository 分层；
2. 必须沿用现有统一返回体和异常处理方式；
3. 若项目已有租户、权限、审计逻辑，必须先复用，再扩展；
4. 数据库 migration 脚本必须沿用现有命名和执行方式；
5. 不允许无关重构；
6. 对不确定的历史逻辑，先列出待确认点，不要擅自猜测。

QUIRK 警告（严格遵守，违反即为 bug）：
7. 若项目约定后端不做字段翻译，严禁在响应中返回 statusName / typeName 等翻译字段；
8. 分页 pageSize 必须与前端 BaseTable 默认值对齐（查看现有模块确认具体值）；
9. 字典服务的 key 类型必须与现有使用方式一致（可能是 String 而非 Integer）。

本次任务：
- [在这里放具体任务]

请先输出：
1. 你理解到的现有模式；
2. 本次改动将落在哪些现有类/模块；
3. 风险点；
4. 再给出实现方案。
```

## 9. 前端实现提示词

```text
你现在在一个历史前端项目中新增/升级页面能力。请优先复用现有页面模式、组件模式和 API 调用模式，不要按新项目方式重做一套界面。

已知约束：
1. 必须沿用当前项目的路由和页面组织方式；
2. 必须沿用现有 API 封装层；
3. 必须沿用现有表单、校验、弹窗、消息提示组件；
4. 若已有设计系统或样式体系，必须复用；
5. 不允许无关的 UI 重构或组件库替换；
6. 若旧页面交互需要兼容，必须明确保留兼容行为。

QUIRK 警告（必须逐条处理，请在输出中列出你注意到的 QUIRK 及应对方式）：
7. 检查 SearchForm 重置后是否自动触发搜索（历史项目中通常不会，需手动查询）；
8. 检查 BaseTable / 分页组件的默认 pageSize（可能是 20 而非 10）；
9. 检查 FormDialog / 弹窗的确认事件是否自动关闭（历史项目中通常不会，需手动关闭）；
10. 检查导出按钮是否自动读取筛选状态（通常不会，需显式传参）；
11. 检查字典服务的 key 类型（可能返回 String 而非 Integer）。

本次任务：
- [在这里放具体任务]

请先输出：
1. 现有页面结构和组件模式；
2. 本次应复用的组件和 API；
3. 可能影响的旧页面；
4. 再给出实现方案。
```

## 10. 前端技能推荐

## 10.1 `frontend-design`

适合：

1. 在既有设计系统中新增页面或改造旧页面；
2. 需要增量优化页面质量；
3. 希望 AI 先总结现有 UI 模式，再设计。

推荐搭配提示词：

```text
请基于当前历史项目的前端风格与组件体系，对目标页面做增量设计与实现优化。

要求：
1. 保留现有设计系统、组件库和交互模式；
2. 新页面或改造页面必须与现有系统视觉风格一致；
3. 优先做增量增强，不做重设计；
4. 输出前先总结你观察到的现有 UI 模式。
```

## 10.2 `webapp-testing`

适合：

1. 做前端 smoke test；
2. 验证旧页面 + 新改动是否一起正常工作；
3. 捕获控制台错误和页面异常。

## 10.3 `context7-mcp`

适合：

1. 历史项目依赖特定版本的 Vue、React、Vite、组件库；
2. 需要查当前版本官方文档；
3. 需要避免 AI 使用过时 API。

## 10.4 `check-compiler-errors`

适合：

1. 前端升级后有编译或类型错误；
2. 需要快速收敛错误清单；
3. 需要按文件和错误类型分组处理。

## 10.5 `requesting-code-review`

适合：

1. 页面改造完成后做规范审查；
2. merge 前做差异级 review；
3. 防止“表面可运行、实际破坏旧模式”。

## 11. 验证与发布提示词

```text
请基于当前 OpenSpec change，对棕地项目改动做最终验证。

验证重点：
1. 新功能 requirement 是否完整覆盖；
2. 旧功能兼容性是否有证据支撑；
3. 前后端关键路径测试是否通过；
4. 数据 migration、回滚点、健康检查和监控项是否准备齐全。

输出要求：
1. 先列 CRITICAL；
2. 再列 WARNING；
3. 每个问题都给整改建议；
4. 若准备就绪，可输出“建议进入发布评审”的结论，但必须同时附：
   - `Change / Commit / PR`
   - 关键测试或验证证据位置
   - 当前环境
   - 剩余风险
   - 仍需谁确认
5. 明确说明“建议进入发布评审”不等于已经批准发布；
6. 如果无法直接执行 `/opsx-verify`，明确给出等价人工验证门禁。
```

## 12. 功能验收矩阵提示词

```text
请基于当前 OpenSpec change、实现状态、测试结果和联调结果，输出功能验收矩阵。

要求：
1. 每条 requirement 和 scenario 单独映射；
2. 明确前端实现、后端实现、前端测试、后端测试、联调验证、发布准备状态；
3. 没有证据的项不能标记为通过；
4. 对 `M-Medium` 和 `L / High Risk`，每条已通过 requirement 至少补：
   - `Change / Commit / PR`
   - `Command Or Action`
   - `Environment`
   - `Evidence Location`
   - `Conclusion`
   - `Residual Risk`
5. 证据优先包含测试结果、请求/响应样例、导出文件样例、日志、截图或 `/opsx-verify` 结果；
6. 最后给出“具备上线评审条件 / 不具备上线评审条件 / 部分达标”的三选一结论，并说明这是基于证据的验收建议，不替代最终人工审批。
```

## 14. QUIRK 信息传递机制

Demo 碰撞验证发现，QUIRK（历史怪癖）信息需要"持久化 + 当次传递"双重机制：

### 14.1 持久化（跨会话）

QUIRK 登记簿写入 `.cursor/rules/quirk-registry.mdc`（alwaysApply），AI 每次新会话自动加载。这是底线保障。

### 14.2 当次传递（当前会话）

在关键提示词（M 级起手、后端实现、前端实现）中，将 QUIRK 作为"QUIRK 警告"段显式嵌入。这比 rules 文件更直接，AI 更容易遵守。

### 14.3 为什么需要双重机制

1. 只靠 mdc 文件：AI 可能不够重视，仍按通用最佳实践生成（Demo 碰撞点 #8 证明）
2. 只靠提示词嵌入：换一个会话就丢了，不可持续
3. 双重机制：mdc 保底 + 提示词强化 = 最可靠

### 14.4 探索结果到后续提示词的衔接

M 级流程中最关键的手动衔接动作：

```
探索输出                    后续提示词
───────                    ──────────
约束清单         →  嵌入到【已知约束】段
QUIRK 清单       →  嵌入到【QUIRK 警告】段
待确认项清单     →  嵌入到【待确认项】段
数据翻译约定     →  嵌入到约束中并强调"严禁违反"
```

不要依赖 AI "记住"上一轮对话。每次新提示词都要手动搬运关键约束。

## 15. 最终口径

在棕地项目里，提示词不是“描述一个功能”，而是“描述一个带历史约束的功能变更”。

你要让 AI 明白的不是：

- “做一个项目管理模块”

而是：

- “在一个已有前后端约定、页面模式、数据库结构和发布流程的历史系统里，增量补齐项目管理模块能力，同时不破坏既有行为，并提供验证和回滚证据。”
