# 棕地项目功能验收矩阵

> 目标：把“功能是否达标”从口头判断变成可检查、可追踪、可沉淀的验收机制。  
> 核心原则：没有 requirement 对应证据，就不能算达成要求。  
> 使用边界：验收矩阵输出的是基于证据的验收结论，不等于自动批准发布；最终仍需人工确认发布评审结论。

在使用本矩阵前，建议先补看：

- `knowledge/core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`

---

## 1. 为什么需要验收矩阵

在棕地项目里，最常见的误判是：

1. 前端页面做出来了，就以为功能完成；
2. 后端接口返回 200，就以为功能可上线；
3. 测试跑了几个 happy path，就以为需求闭环；
4. 代码合并了，就以为功能达标。

这些都不够。

真正能回答“功能是否达到要求”的，不是单条测试，也不是一句“完成了”，而是一张验收矩阵：

- requirement 是否被正式定义
- 前端是否实现
- 后端是否实现
- 测试是否覆盖
- 联调是否跑通
- 发布是否具备条件
- 是否有证据沉淀

---

## 2. 验收矩阵的使用方式

每个功能模块都应该建立一张矩阵。  
矩阵建议在三个时间点更新：

1. **OpenSpec 完成后**：先建立 requirement 骨架；
2. **开发进行中**：边实现边补充前后端、测试、联调状态；
3. **发布前**：补齐最终验证、发布准备和结论。

## 2.1 矩阵也要服从治理分流

不是所有需求都需要同样强度的矩阵证据。  
建议按：

- `knowledge/core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`

先判断当前需求属于：

1. `S-Low`
2. `M-Medium`
3. `L / High Risk`

建议口径：

1. `S-Low`：保留最小验证记录即可，不必强行展开完整矩阵；
2. `M-Medium`：建议建立精简但完整的 requirement 级矩阵；
3. `L / High Risk`：使用本文的完整矩阵和完整证据要求。

---

## 3. 标准矩阵模板

建议字段如下：

| Requirement | Scenario | 前端实现 | 后端实现 | 前端测试 | 后端测试 | 联调验证 | 发布准备 | 状态 | 证据 | 备注 |
|---|---|---|---|---|---|---|---|---|---|---|

### 字段说明

#### Requirement

来自 OpenSpec `spec.md` 的 requirement 名称。

#### Scenario

来自 OpenSpec 的 scenario，用来定义更细的验收粒度。

#### 前端实现

写清该 requirement 对应的页面、组件、交互是否完成。

#### 后端实现

写清该 requirement 对应的接口、服务、数据处理是否完成。

#### 前端测试

写清前端是否已有组件测试、页面测试、浏览器验证。

#### 后端测试

写清后端是否已有单测、接口测试、回归测试。

#### 联调验证

写清前后端是否一起跑通过。

#### 发布准备

写清 migration、监控、回滚、配置是否具备。

#### 状态

建议只用以下状态，不要用模糊词：

- `未开始`
- `进行中`
- `前端完成`
- `后端完成`
- `联调通过`
- `验证通过`
- `阻塞`

#### 证据

这里只放真实证据，例如：

- 测试命令结果
- 请求/响应样例
- HAR / 接口录屏 / 浏览器网络证据
- 截图
- 日志
- PR 链接
- 导出文件样例
- `/opsx-verify` 结果

为了避免“贴了很多材料但无法追溯”，建议把证据进一步结构化，至少补齐：

1. `Change / Commit / PR`
2. `Command Or Action`
3. `Environment`
4. `Result`
5. `Evidence Location`
6. `Conclusion`
7. `Residual Risk`

#### 备注

写兼容性问题、例外、待确认项。

## 4. 状态判定规则

为了避免“说完成但其实没闭环”，建议统一采用下面的判定规则：

### `前端完成`

满足：

1. 页面或交互已实现；
2. 符合项目规则基线；
3. 已有前端自测证据。

### `后端完成`

满足：

1. 接口和服务已实现；
2. 校验、异常、权限、租户等约束已接入；
3. 已有后端测试证据；
4. 关键请求/响应契约已有样例或测试覆盖证据。

### `联调通过`

满足：

1. 前后端一起跑通；
2. 关键场景和异常场景至少已验证一次；
3. 旧链路回归已执行，并且证据中写明实际回归范围、结果和证据位置；若仅抽样验证，必须在备注中写明残余风险；
4. 权限、租户、主数据等高风险场景至少有一条联调证据。

### `验证通过`

满足：

1. `/opsx-verify` 无关键阻塞，或已完成等价人工验证门禁；
2. 若环境无 `/opsx-*`，等价门禁至少补齐测试结果、联调结果、旧链路回归结果、发布准备证据和结构化证据块；
3. 测试、联调、回归、发布准备都有证据；
4. requirement 已形成闭环。

### `阻塞`

满足任一项：

1. spec 不完整；
2. 需求存在遗漏；
3. 联调未通过；
4. 缺少关键测试；
5. 发布准备不完整。

## 6. 项目管理模块示例

下面给一个更贴近实战的例子：棕地项目中新增“项目管理”模块，功能包括：

1. 列表查询
2. 新增
3. 修改
4. 导出

### 示例矩阵

```md
## 项目管理模块功能验收矩阵

| Requirement | Scenario | 前端实现 | 后端实现 | 前端测试 | 后端测试 | 联调验证 | 发布准备 | 状态 | 证据 | 备注 |
|---|---|---|---|---|---|---|---|---|---|---|
| Query Project List | 按项目名称和状态筛选列表 | 列表页、查询区已完成 | 列表查询接口已完成 | 页面筛选测试已执行 | 查询接口测试已执行 | 已按筛选条件联调通过 | 无特殊发布项 | 联调通过 | 页面截图、接口响应样例、测试结果 | 需确认是否补充创建时间筛选 |
| Create Project | 新增项目并校验必填项 | 新增弹窗已完成 | 新增接口已完成 | 表单校验测试已执行 | 新增接口测试已执行 | 提交后列表已刷新 | 无特殊发布项 | 联调通过 | 页面录屏、请求/响应样例、测试结果 | 负责人字段依赖主数据服务 |
| Update Project | 修改项目信息并回显原数据 | 编辑弹窗已完成 | 修改接口已完成 | 回显测试已执行 | 修改接口测试已执行 | 修改后列表已刷新 | 无特殊发布项 | 联调通过 | 页面截图、接口响应、租户范围验证记录 | 需确认修改权限范围 |
| Export Project List | 按当前筛选条件导出 | 导出按钮已完成 | 导出接口/服务已完成 | 导出交互测试已执行 | 导出测试已执行 | 已导出符合当前筛选的文件 | 需确认导出文件命名规范 | 进行中 | 导出文件样例、日志、网络请求证据 | 还缺发布前导出文件校验 |
```

### 如何解读这个示例

这个矩阵告诉你：

1. 列表查询、新增、修改都已前后端闭环；
2. 导出功能虽然前后端都做了，也联调过，但发布准备还未完全闭环；
3. 所以整个模块不能笼统说“全部完成”，更准确说法是：
   - 主流程基本闭环
   - 导出功能仍有发布前校验项未完成

这就是矩阵的价值。

## 7. 如何把矩阵接入现有流程

## 7.1 在 OpenSpec 之后建立初版矩阵

提示词：

```text
请基于当前 OpenSpec change，为本次功能建立一份验收矩阵。

要求：
1. 每条 requirement 和 scenario 都要单独列出；
2. 映射对应的前端实现、后端实现、前端测试、后端测试、联调验证；
3. 对没有对应测试或证据的项，明确标记为“缺失”；
4. 输出结果要能直接用于判断功能是否达标。
```

## 7.2 在开发过程中持续更新

提示词：

```text
请基于当前实现进度，更新功能验收矩阵。

要求：
1. 只更新本次迭代实际变化的 requirement；
2. 明确哪些 requirement 已到“前端完成”“后端完成”“联调通过”；
3. 没有证据的项不得标记为通过；
4. 对 `M-Medium` 和 `L / High Risk` 场景，优先补结构化证据块而不是只写一句“已验证”；
5. 明确指出当前阻塞项。
```

## 7.3 在发布前输出最终结论

提示词：

```text
请基于当前项目规则基线、OpenSpec change、测试结果和联调结果，输出功能验收结论。

要求：
1. 以验收矩阵为依据；
2. 明确哪些 requirement 已闭环；
3. 明确哪些 requirement 仍存在缺口；
4. 输出“具备上线评审条件 / 不具备上线评审条件 / 部分达标”的结论；
5. 结论必须有证据支撑；
6. 对高风险项明确列出剩余风险；
7. 明确这只是基于证据的验收建议，不替代最终人工审批。
```

## 7.4 不同风险等级的证据强度

### `S-Low`

至少保留：

1. 关键验证动作；
2. 结果；
3. 结论；
4. 剩余风险。

### `M-Medium`

至少保留：

1. `Change / Commit / PR`
2. 关键测试或验证命令；
3. 环境；
4. 结果；
5. 证据位置；
6. requirement 结论；
7. 剩余风险。

### `L / High Risk`

至少保留：

1. 完整 change / commit / PR 关联；
2. 测试证据；
3. 联调证据；
4. 导出或高风险场景证据；
5. 发布准备证据；
6. requirement 结论；
7. 剩余风险与人工判断。

## 8. 自动化评估可以做到什么程度

需要严谨说明的是：

### 可以自动化的部分

1. 编译、构建
2. 后端测试
3. 前端测试
4. smoke test
5. `/opsx-verify`
6. 导出文件基础校验
7. 回归测试结果汇总

### 不应该假装全自动的部分

1. RP / 设计稿的视觉符合度
2. 某些复杂业务语义是否真正满足
3. 上线后的业务效果评估

所以最合理的做法是：

> 自动化验收门禁 + 人工业务验收补位

---

## 9. 最终结论

如果你想真正知道“功能有没有达到要求”，最有效的不是再加一句“请仔细检查”，而是强制使用验收矩阵。

一句话总结：

> 功能完成的定义，不是“代码写完”，而是“每条 requirement 都有实现、有测试、有联调、有证据”。
