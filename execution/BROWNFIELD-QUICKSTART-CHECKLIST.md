# 棕地项目 AI 开发快速清单

> 适用场景：你接手一个不了解的历史项目，想基于 `OpenSpec + Superpowers + 项目规则基线` 快速推进一个新增或升级功能。  
> 用法：按顺序执行，不跳步。每一步只要达到“完成标准”再进入下一步。

---

## 0. 开始前确认

先确认三件事：

1. 这是棕地项目，不是新项目。
2. 目标功能已经确定，例如 `项目管理模块`。
3. 你接受一个原则：
   - 先理解现状，再设计，再实现。

如果你不确定当前环境是否能直接使用 `/opsx-*` 或 Superpowers，请先看：

- `execution/AI-WORKFLOW-TOOLING-PREREQUISITES.md`

---

## 1. 巡查项目整体结构

### 目标

快速摸清技术栈、分层、前后端模式、测试方式、发布方式。

### 推荐动作

先用 `/opsx-explore` 或等价 explore 流程进入棕地项目探索模式，再做结构巡查。

### 最小提示词

```text
请先不要设计或实现功能。先基于当前历史项目做结构巡查。

请输出：
1. 后端技术栈、分层、返回体、异常、安全、租户、测试模式；
2. 前端技术栈、路由、页面组织、组件模式、API 封装、状态管理、样式体系；
3. 数据库迁移方式、配置方式、发布方式；
4. 兼容性风险和可能影响的旧链路。

要求：
1. 先描述现状；
2. 不给重构方案；
3. 每条关键结论附真实文件路径；
4. 至少给出一条真实调用链或页面到接口链；
5. 不确定内容标注为待确认。
```

### 完成标准

你已经拿到一份带证据的“项目现状摘要”。

---

## 2. 提炼规则基线

### 目标

把“现状”提炼成“后续 AI 必须遵守的规则”。

### 最小提示词

```text
请基于刚才的巡查结果，提炼一套棕地项目统一规则基线。

请分三层输出：
1. 项目级规则；
2. 后端规则；
3. 前端规则。

要求：
1. 规则来自当前项目真实现状；
2. 能约束后续 AI 行为；
3. 用“必须 / 不得 / 先确认再修改”表达；
4. 最后说明这些规则主要防止哪些常见错误。
```

### 完成标准

你已经拿到一份“规则基线”。

---

## 3. 固化为 Cursor 规则

### 目标

让后续 AI 会话自动加载或参考这些规则。

### 最小提示词

```text
请基于当前项目规则基线，生成三类 Cursor rules：
1. 项目级 alwaysApply 规则；
2. Java 后端规则；
3. 前端规则（Vue/React/TS/JS）。

要求：
1. 使用 .mdc 格式；
2. 内容简短、明确、可执行；
3. 后端规则覆盖分层、异常、返回体、测试、兼容性；
4. 前端规则覆盖路由、页面、组件、API、样式、兼容性。
```

### 完成标准

`.cursor/rules/*.mdc` 已生成并生效。

---

## 4. 需求澄清

### 目标

把功能边界讲清楚，不要直接开始编码。

### 最小提示词

```text
请基于当前项目规则基线，帮助我澄清一个棕地项目中的新增功能：项目管理模块。

已知范围：
1. 列表查询
2. 新增
3. 修改
4. 导出

要求：
1. 一次只问一个关键问题；
2. 优先问兼容性、影响范围、旧链路、非目标和回滚要求；
3. 不进入数据库设计或代码实现。

当信息足够时，请输出：
1. 需求摘要；
2. 当前行为；
3. 目标行为；
4. 必须兼容的旧行为；
5. 风险和回滚点；
6. 待确认问题。
```

### 完成标准

你已经明确：

1. 当前行为
2. 目标行为
3. 兼容要求
4. 风险
5. 待确认问题

## 5. 进入 OpenSpec

### 目标

让 `OpenSpec` 在当前 change 范围内成为唯一规格真相源。

### 当前主示例路径

如果你想边做边对照当前主案例，优先参考：

1. `openspec/changes/project-management/proposal.md`
2. `openspec/changes/project-management/design.md`
3. `openspec/changes/project-management/tasks.md`
4. `openspec/changes/project-management/specs/project-management/spec.md`

### 最小提示词

```text
请基于当前项目规则基线，为 `project-management` 生成功能变更的 OpenSpec artifacts：
1. proposal
2. spec
3. design
4. tasks

要求：
1. capability 使用 `project-management`；
2. proposal 写清受影响旧链路和兼容边界；
3. spec 必须有兼容性场景；
4. design 必须写复用哪些现有模块；
5. tasks 必须包含调研、后端、前端、联调、验证、发布准备。
```

### 完成标准

你已经有：

1. `proposal.md`
2. `spec.md`
3. `design.md`
4. `tasks.md`

如果不知道应该写成什么样，直接对照当前主示例 change：

- `openspec/changes/project-management/`

## 6. 进入 Superpowers 计划阶段

### 目标

把 OpenSpec 任务翻译成可执行计划。

### 最小提示词

```text
请基于当前项目规则基线和 `project-management` 的 OpenSpec artifacts 生成实施计划。

要求：
1. 这是棕地项目；
2. 计划必须先处理兼容性，再处理后端、前端、联调；
3. 每个任务都要说明复用哪些旧模块、影响哪些旧链路、怎么验证；
4. 后续执行按 subagent-driven-development 组织。
```

### 完成标准

你已经有一份可执行实施计划。

---

## 7. 多角色开发

### 目标

在规则基线和 OpenSpec 双重约束下推进实现。

### 最小提示词

```text
请按 subagent-driven-development 执行 `project-management` 变更，并始终遵守当前项目规则基线。

要求：
1. 每个任务开始前，先说明复用哪些旧模块、影响哪些旧链路；
2. 每个任务完成后，先做 spec review，再做 code quality review；
3. review 时必须检查兼容性，不只是检查新功能；
4. 没有验证证据，不要进入下一个任务；
5. 若发现历史实现与 spec 假设不一致，暂停并更新 OpenSpec。
```

### 完成标准

后端、前端、联调任务都已完成，并通过 review。

---

## 8. 联调与测试

### 目标

确认新功能可用，旧链路没坏。

### 最小提示词

```text
请基于当前项目规则基线，对“项目管理模块”功能做联调和测试设计。

要求：
1. 同时覆盖列表查询、新增、修改、导出、联调 smoke test、旧链路回归；
2. 输出关键测试场景、兼容性回归场景、验证步骤和测试证据要求；
3. 不只验证新功能，也要验证旧页面和旧接口未被破坏。
```

### 完成标准

你已经拿到并执行了：

1. 新功能测试
2. 旧链路回归测试
3. smoke test

---

## 9. 发布准备

### 目标

确认功能具备上线条件。

### 最小提示词

```text
请基于当前项目规则基线和 `project-management` 变更，生成发布准备清单。

要求：
1. 同时覆盖后端、前端、数据库；
2. 明确配置项、migration、健康检查、监控项、回滚点；
3. 明确棕地项目中的旧链路观察项；
4. 输出结果要能直接作为上线执行清单。
```

### 完成标准

发布清单、回滚点、监控点都已明确。

## 10. Git 提交、代码评审、PR 与合并

### 目标

把开发结果真正转成可评审、可合并、可发布的代码状态。

### 最小提示词

```text
请基于当前项目规则基线和 `project-management` change，帮我准备 git 提交、代码评审和 PR 合并流程。

请输出：
1. 功能分支命名建议；
2. 当前适合提交哪些 focused commit；
3. 每次 commit 前应完成哪些验证；
4. PR 标题和 PR 描述；
5. PR 合并前必须检查的事项；
6. 合并后还需要补哪些验证和文档动作。
```

### 完成标准

你已经具备：

1. 独立功能分支；
2. focused commit 方案；
3. PR 描述；
4. 合并前检查清单。

## 11. 最终验证

### 目标

在上线前做最后一次证据式确认。

### 最小提示词

```text
请基于当前项目规则基线和 `project-management` 的 OpenSpec change，对当前实现做最终验证。

验证重点：
1. Completeness
2. Correctness
3. Coherence
4. Compatibility
5. Release readiness

输出要求：
1. 使用 CRITICAL / WARNING / SUGGESTION 分类；
2. 每个问题给整改建议；
3. 如果满足上线条件，只能输出“建议进入发布评审”及依据；
4. 明确该结论不等于已批准上线，仍需人工确认。
```

### 完成标准

验证报告显示当前没有阻塞发布评审的关键问题，并且已给出证据位置、剩余风险和人工确认前提。

## 12. 上线执行

### 目标

真正发布功能。

### 最小提示词

```text
请基于当前项目规则基线，生成“项目管理模块”功能的上线执行步骤。

要求：
1. 按时间顺序输出：
   - 发布前检查
   - 数据库处理
   - 后端发布
   - 前端发布
   - 发布后验证
   - 监控观察
   - 回滚触发条件
2. 明确哪些步骤是棕地项目发布里必须保留的；
3. 输出结果要适合直接执行。
```

### 完成标准

上线步骤、观察项、回滚触发条件都明确。

---

## 14. 归档与沉淀

### 目标

让这次功能真正闭环，并把经验反哺到规则基线。

### 最小提示词

```text
请基于当前项目规则基线，对 `project-management` 变更做收尾建议。

要求：
1. 说明是否满足 OpenSpec 归档条件；
2. 说明是否需要同步主 specs；
3. 总结这次实现中新增的项目约束或经验，判断是否要反写到 rules；
4. 输出：
   - 归档建议
   - 规则更新建议
   - 后续迭代建议
```

### 完成标准

完成归档，并决定是否更新规则基线。

## 15. 一页式执行顺序

真正开工时，只看这几步：

1. 用 `/opsx-explore` 探索项目
2. 巡查项目
3. 提炼规则
4. 固化 rules
5. 澄清需求
6. 写 OpenSpec
7. 写 Superpowers 计划
8. 多角色开发
9. 联调测试
10. Git 提交、评审、PR、合并
11. 发布准备
12. 最终验证
13. 上线
14. 归档

### 当前主案例参考入口

执行过程中如需参考主案例，优先看：

1. `execution/PROJECT-MANAGEMENT-BROWNFIELD-EXECUTION-PROMPTS.md`

3. `openspec/changes/project-management/`

## 16. 最关键的一句话

不要这样问：

- “帮我做一个项目管理模块”

要这样问：

- “请基于当前项目规则基线，在这个历史系统里增量加入项目管理模块，并保证不破坏既有前后端模式、旧链路和发布约束。”
