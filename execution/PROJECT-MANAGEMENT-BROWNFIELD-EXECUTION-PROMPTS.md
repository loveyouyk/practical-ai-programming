# 项目管理模块棕地项目执行提示词手册

> 适用前提：你已经完成棕地项目巡查，已经提炼出前后端统一规则基线，并且 `.cursor/rules/*.mdc` 已生效。  
> 目标：从第 7 步开始，基于既有规则基线，在历史项目中一步步推进 `项目管理模块` 新功能，从需求澄清到上线归档。  
> 使用边界：这份手册提供执行提示词模板，不替代 `OpenSpec artifacts`、验收矩阵、交付模板和最终人工确认。

如果下面任一项尚未满足，则不要直接从第 7 步开始：

1. 当前需求还未完成治理分流判断
2. 棕地项目巡查还未完成
3. 项目规则基线还未形成
4. 工具环境可用性还未确认

此时应先返回：

1. `knowledge/core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`
2. `knowledge/execution/BROWNFIELD-RULE-BASELINE-PLAYBOOK.md`
3. `knowledge/execution/AI-WORKFLOW-TOOLING-PREREQUISITES.md`

在使用本手册前，建议先补看：

1. `knowledge/core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`
2. `knowledge/core/PROJECT-MANAGEMENT-DOC-MAP.md`
3. `knowledge/execution/PROJECT-MANAGEMENT-OPENSPEC-SUPERPOWERS-SPEC-GUIDE.md`

如果你不确定当前环境是否能直接使用 `/opsx-*` 或某些 Superpowers 能力，请先补看：

4. `knowledge/execution/AI-WORKFLOW-TOOLING-PREREQUISITES.md`

---

## 1. 使用说明

这份手册不是用来“提炼规则”的，而是用来“带着规则做功能”。

更准确地说：

1. 它默认服务于 `L / High Risk` 场景；
2. 也适用于在 `M-Medium` 审批中被升级为高风险的场景；
3. 不建议 `S-Low` 需求默认直接套用本手册全流程。

从现在开始，你的所有提示词都默认包含一个隐藏前提：

> 请基于当前项目规则基线执行，不要按绿地项目方式重做。

另外，在棕地项目里，建议把 `/opsx-explore` 视为正式执行前的默认前置动作之一，用来做现状地图、复用关系和兼容性风险识别。

## 1.1 进入本手册前先做分流判断

正式进入第 7 步前，应先按：

- `knowledge/core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`

判断当前需求属于哪条路径：

1. `S-Low`：不默认进入本手册全流程；
2. `M-Medium`：优先走最小探索 + 最小 OpenSpec + 快速审批；
3. `L / High Risk`：进入本手册的完整执行路径。

如果 `M-Medium` 在审批过程中出现以下任一情况，也应切换到本手册完整流程：

1. 边界不清；
2. 主数据来源不清；
3. 字段契约不清；
4. 旧链路影响超出预期；
5. 验证项明显不足；
6. 风险高于原先评估。

推荐执行顺序：

1. 需求澄清
2. OpenSpec 变更产物
3. Superpowers 实施计划
4. 多角色开发
5. 联调与测试
6. Git 提交、代码评审、PR 与合并
7. 发布准备
8. 最终验证
9. 上线执行
10. 归档沉淀

## 2. 第 7 步：需求澄清

### 目标

把 `项目管理模块` 在棕地项目里的边界讲清楚，而不是直接进入实现。

### 推荐前置动作

在正式做需求澄清前，建议先用 `/opsx-explore` 或等价 explore 流程做一次面向 `项目管理模块` 的现状探索，先确认：

1. 系统里是否已有相近项目、客户、合同、组织或导出能力；
2. 前端哪些页面和组件可能会被复用或影响；
3. 后端哪些接口、Service、Mapper、表结构最相关；
4. 旧链路最大的兼容性风险点是什么。

### Explore 提示词

```text
请先进入棕地项目探索模式，不要设计新功能，也不要写代码。请用探索视角帮我理解这个历史项目与“项目管理模块”需求相关的现状。

请重点找出：
1. 相关前端页面入口、路由、共享组件和 API 调用链；
2. 相关后端 Controller、Service、Mapper、数据库表；
3. 旧页面、旧接口、旧数据结构之间的复用关系；
4. 已有测试、发布脚本、migration 和历史文档；
5. 哪些地方最可能成为新增“项目管理模块”时的兼容性风险；
6. 项目状态、负责人、客户、组织等字段是否已有主数据来源或字典来源；
7. 导出能力是否已有统一实现。

输出要求：
1. 先输出“现状地图”；
2. 再输出“高风险点”；
3. 再输出“需要继续确认的问题”；
4. 每条关键结论至少附一个真实文件路径；
5. 至少给出一条真实调用链、依赖链或页面到接口链；
6. 不确定结论明确标记为 `待确认`；
7. 不给实现方案。
```

### 提示词

```text
请基于当前项目规则基线，帮助我澄清一个棕地项目中的新增功能：项目管理模块。

注意：
1. 当前项目是历史项目，不是新项目；
2. 已有项目规则基线已经存在，请默认遵守；
3. 不要直接进入数据库设计或代码实现；
4. 一次只问一个关键问题，优先问兼容性、影响范围、受影响旧链路和非目标。

已知本次功能至少包括：
1. 列表查询
2. 新增
3. 修改
4. 导出

请围绕以下内容逐步收敛：
1. 为什么要新增项目管理模块；
2. 目标用户是谁；
3. 现有系统里是否已有相近项目/列表/导出能力；
4. 新增项目管理模块会影响哪些旧页面、旧接口、旧数据结构；
5. MVP 范围是什么；
6. 非目标是什么；
7. 上线方式、灰度方式、回滚要求是什么。

当信息足够时，请输出：
1. 需求摘要；
2. 当前行为；
3. 目标行为；
4. 必须兼容的旧行为；
5. 风险和回滚点；
6. 待确认问题。
```

### 完成标准

只有当 AI 明确输出了：

1. 当前行为
2. 目标行为
3. 兼容性要求
4. 风险
5. 待确认问题
6. 关键结论对应的真实文件路径
7. 至少一条关键调用链证据

才进入第 8 步。

## 3. 第 8 步：进入 OpenSpec

### 目标

把需求沉淀为正式 change，使 `OpenSpec` 在当前 change 范围内成为唯一规格真相源。

## 3.1 先生成“现状与变更背景”

```text
请基于刚才已经确认的“项目管理模块”需求，并严格遵守当前项目规则基线，为这个棕地项目先整理一份“现状与变更背景”。

要求：
1. 先写当前系统已有能力；
2. 再写当前前后端链路；
3. 再写当前数据库、接口、页面约束；
4. 再写本次项目管理模块的目标行为；
5. 再写必须兼容的旧行为；
6. 最后写风险和回滚点。

输出格式请适合作为 OpenSpec proposal 和 design 的输入。
```

## 3.2 生成 OpenSpec proposal

```text
请基于当前项目规则基线和刚才整理好的“现状与变更背景”，为新增功能 `project-management` 生成 OpenSpec proposal。

要求：
1. 这是棕地项目增量扩展，不是新系统建设；
2. capability 使用 `project-management`；
3. proposal 中必须写清：
   - 为什么做
   - 会复用哪些现有链路
   - 会影响哪些旧页面、旧接口、旧数据结构
   - 非目标
   - 风险和兼容边界
4. 不要写具体实现代码。
```

## 3.3 生成 OpenSpec spec

```text
请基于当前项目规则基线，为新增功能 `project-management` 生成 OpenSpec spec。

要求：
1. 使用 ADDED Requirements；
2. requirement 至少覆盖：
   - Query Project List
   - Create Project
   - Update Project
   - Export Project List
3. 每个 requirement 都要考虑棕地项目兼容性；
4. 至少补充以下场景：
   - 列表筛选场景
   - 表单校验失败场景
   - 导出按当前筛选条件生效场景
   - 旧权限、旧字典、旧数据来源不受破坏的兼容性场景
5. requirement 同时覆盖前端体验和后端行为。
```

## 3.4 生成 OpenSpec design

```text
请基于当前项目规则基线，为 `project-management` 生成 OpenSpec design。

要求：
1. 先说明现有系统结构和限制；
2. 再说明本次项目管理模块会复用哪些现有前后端模块；
3. 后端必须说明：
   - 列表查询链路
   - 新增/修改接口契约
   - 请求/响应字段示例
   - 导出实现复用方式
   - 字典/主数据来源
   - 权限、租户、校验、异常处理
4. 前端必须说明：
   - 页面入口
   - 路由挂载位置
   - 查询区与列表表格
   - 新增/修改表单
   - 导出按钮与反馈
   - RP 原型如何映射到现有页面模式
5. 必须写清兼容策略、验证策略、回滚策略；
6. 对 API 路径如仍是占位表达，必须显式标注“待在探索后以真实路径替换”；
7. 不允许脱离现有项目模式重做一套前后端结构。
```

## 3.5 生成 OpenSpec tasks

```text
请基于当前项目规则基线和已有 proposal/spec/design 生成 OpenSpec tasks。

要求：
1. 按以下顺序分组：
   - Brownfield Discovery
   - Backend List Query
   - Backend Create/Update
   - Backend Export
   - Frontend List Page
   - Frontend Form
   - Frontend Export
   - Integration
   - Verification
   - Release Preparation
2. 每个任务都要体现兼容性考虑；
3. 不要写成抽象口号；
4. 任务粒度要适合后续交给 Superpowers writing-plans 继续展开。
```

### 完成标准

只有满足下面条件，才算 OpenSpec 第 8 步完成：

1. `proposal.md`
2. `spec.md`
3. `design.md`
4. `tasks.md`
5. 四份 artifacts 之间不存在明显冲突
6. 待确认项已经显式列出，而不是被 AI 默认补全
7. 已完成至少一轮人工评审，明确当前 artifacts 可进入实施计划阶段

## 4. 第 9 步：进入 Superpowers 实施计划阶段

### 目标

把 OpenSpec 的任务翻译成可执行工程计划。

### 提示词

```text
请基于当前项目规则基线和 `project-management` 的 OpenSpec artifacts（proposal/spec/design/tasks）生成实施计划。

要求：
1. 这是棕地项目，不是新项目；
2. 计划必须先处理兼容性和现状约束，再处理后端、前端、联调；
3. 如果实施计划与 OpenSpec artifacts 冲突，以 OpenSpec 为准，并先回写或重生计划；
4. 每个任务都要说明：
   - 会复用哪些现有模块
   - 会影响哪些旧链路
   - 要改哪些类型的文件
   - 要做哪些测试
   - 如何验证
5. 执行顺序建议为：
   - 后端列表查询
   - 后端新增/修改
   - 后端导出
   - 前端列表页
   - 前端查询区
   - 前端新增/修改表单
   - 前端导出按钮
   - 联调
   - 验证
   - 发布准备
6. 后续执行方式按 subagent-driven-development 组织。
```

### 完成标准

你拿到的是“实施计划”，不是代码。

---

## 5. 第 10 步：进入多角色开发

### 目标

在规则基线和 OpenSpec 双重约束下推进实现。

## 5.1 后端实现者提示词

```text
你现在扮演棕地项目中的后端实现者，请基于当前项目规则基线和 `project-management` 的 OpenSpec artifacts 实现后端任务。

要求：
1. 严格遵循现有 Controller / Service / Mapper(Repository) 分层；
2. 沿用统一返回体、异常处理、权限/租户/审计逻辑；
3. 优先复用现有模块，不做无关重构；
4. 项目管理模块后端至少要支持：
   - 列表查询
   - 新增
   - 修改
   - 导出
   - 按项目名称、项目编号、状态、负责人、创建时间等条件筛选
5. 先输出：
   - 当前任务要复用哪些现有类/模块
   - 可能影响哪些旧链路
   - 风险点
6. 再输出实现方案；
7. 最后给出测试方案和验证方式。
```

## 5.2 前端实现者提示词

```text
你现在扮演棕地项目中的前端实现者，请基于当前项目规则基线和 `project-management` 的 OpenSpec artifacts 实现前端任务。

要求：
1. 复用现有路由、页面结构、组件模式、API 封装、表单校验、消息提示；
2. 不替换组件库、状态管理和样式体系；
3. 项目管理模块前端至少要支持：
   - 列表展示
   - 条件筛选
   - 新增
   - 修改
   - 导出当前筛选结果
4. 必须兼容旧页面交互；
5. 先输出：
   - 现有页面结构和可复用组件
   - 本次会影响哪些旧页面或公共组件
   - 风险点
6. 再输出实现方案；
7. 最后给出前端测试和浏览器验证方式。
```

## 5.3 Spec Reviewer 提示词

```text
你现在扮演 Spec Reviewer，请基于 `project-management` 的 OpenSpec artifacts 和当前项目规则基线，检查当前实现是否符合规格。

检查重点：
1. 是否完整覆盖 `project-management` 的 requirement；
2. 是否遗漏了兼容性场景；
3. 导出是否真正按当前筛选条件生效；
4. 是否前后端围绕同一个 capability；
5. 是否破坏了旧页面、旧接口、旧权限或旧主数据来源。

输出要求：
1. 先列出 CRITICAL；
2. 再列出 WARNING；
3. 每个问题都必须对应 requirement 或 scenario；
4. 不讨论代码风格，只讨论规格一致性。
```

## 5.4 Code Quality Reviewer 提示词

```text
你现在扮演 Code Quality Reviewer，请基于当前项目规则基线检查这次“项目管理模块”改动的质量。

检查重点：
1. 是否遵循现有项目结构和模式；
2. 是否存在无关重构；
3. 列表、表单、导出是否复用了该复用的公共逻辑；
4. 错误处理、权限、租户、校验、测试是否完整；
5. 前端是否复用了既有页面、组件、API 和导出交互模式；
6. 是否存在棕地项目里高风险的兼容性问题。

输出要求：
1. 按严重程度排序；
2. 重点指出结构、兼容性、健壮性问题；
3. 不重复 spec reviewer 已经覆盖的问题。
```

## 6. 第 11 步：联调与测试

### 目标

确认新功能可用，旧链路不坏。

### 提示词

```text
请基于当前项目规则基线，对“项目管理模块”功能做联调和测试设计。

要求：
1. 同时覆盖：
   - 列表查询
   - 新增
   - 修改
   - 导出
   - 权限与租户场景
   - 主数据 / 字典校验场景
   - 前后端联调 smoke test
   - 旧链路回归验证
2. 输出：
   - 关键测试场景
   - 兼容性回归场景
   - 验证步骤
   - 需要保留的测试证据
   - 请求/响应样例证据
3. 不只验证新功能，要显式验证旧页面和旧接口未被破坏。
```

### 功能验收矩阵提示词

```text
请基于当前项目规则基线、`project-management` 的 OpenSpec change、当前实现状态、测试结果和联调结果，输出一份功能验收矩阵。

要求：
1. 每条 requirement 和 scenario 都要单独映射；
2. 每条 requirement 至少说明：
   - 前端实现状态
   - 后端实现状态
   - 前端测试状态
   - 后端测试状态
   - 联调验证状态
   - 发布准备状态
3. 没有证据的项不能标记为通过；
4. 明确哪些 requirement 已闭环，哪些仍有缺口；
5. 最后给出：
   - 建议进入发布评审
   - 不建议进入发布评审
   - 部分达标
   三选一结论，并说明依据；
6. 结论必须附 `Change / Commit / PR`、关键证据位置、环境和剩余风险；
7. 明确该结论只是验收建议，不替代最终人工审批。
```

### 证据要求

这里的“通过”不能只靠口头说明。  
对不同风险等级，最低证据要求建议固定如下：

1. `S-Low`：至少保留
   - 一条关键验证动作
   - 一条结果证据
   - 一条剩余风险说明
2. `M-Medium`：至少保留
   - 后端测试或前端验证结果
   - 联调结果
   - 旧链路回归结果
   - `Change / Commit / PR`
   - 证据位置与结论
3. `L / High Risk`：至少保留
   - 后端测试结果
   - 前端验证结果
   - 前后端联调结果
   - 旧链路回归结果
   - `/opsx-verify` 或等价验证结果
   - 导出文件、截图、日志、录屏、PR 说明等交付证据

### 完成标准

只有当你能清楚回答下面 4 个问题，才算真正完成第 11 步：

1. 哪些 requirement 已经前后端闭环；
2. 哪些 requirement 还没有证据支撑；
3. 哪些 requirement 仍然阻塞发布；
4. 整个功能当前是否仅“建议进入发布评审”，还是仍不具备条件。

## 7. 第 12 步：发布准备

### 目标

让功能形成进入发布评审的准备条件，而不是直接替代发布审批。

### 提示词

```text
请基于当前项目规则基线和 `project-management` 变更，生成发布准备清单。

要求：
1. 同时覆盖后端、前端、数据库；
2. 明确：
   - 配置项
   - migration
   - 健康检查
   - smoke test
   - 监控项
   - 回滚点
3. 若这是棕地项目中的增量能力，必须明确旧链路观察项；
4. 输出要能直接作为上线执行清单。
```

## 8. Git 提交、代码评审、PR 与合并

### 目标

把“功能开发完成”真正转成“可评审、可合并、可发布”的代码状态。

### 推荐顺序

1. 在独立功能分支上完成开发；
2. 完成当前 change 对应验证；
3. 提交 focused commit；
4. 发起代码评审；
5. 推送并创建 PR；
6. 合并到基线分支；
7. 合并后再次验证；
8. 再进入正式发布。

### 功能分支与提交策略提示词

```text
我们已经完成规则基线、需求澄清和 OpenSpec 设计。现在准备正式进入实现，请按棕地项目规范给出建议的 git 工作方式。

要求：
1. 基于当前 change `project-management` 建议一个功能分支命名；
2. 说明哪些阶段适合提交 commit；
3. 每次 commit 前应该验证什么；
4. 保证本次分支只承载“项目管理模块”这一组变更，不混入无关修改。
```

### Commit 整理提示词

```text
请基于当前项目规则基线和 `project-management` change，帮我整理本次待提交改动。

要求：
1. 先判断这些改动是否已经通过对应验证；
2. 如果验证不够，先指出缺口，不要急着提交；
3. 如果可以提交，请建议：
   - 这次 commit 应该包含哪些文件类型
   - 这次 commit 的主题是什么
   - 这次 commit 为什么应该独立存在
4. 提交说明应反映本次 change 的真实范围，不要夸大。
```

### Code Review / PR 提示词

```text
请基于当前项目规则基线、`project-management` 的 OpenSpec artifacts 和当前差异，帮我准备代码评审说明和 PR 描述。

请输出：
1. 这次变更做了什么；
2. 明确没做什么；
3. 哪些旧链路被重点保护；
4. 做了哪些验证；
5. 评审人最应该关注哪些兼容性风险；
6. 一个真实可用的 PR 标题；
7. 一个真实可用的 PR Summary 和 Test Plan。
```

### PR 合并前检查提示词

```text
请基于当前项目规则基线，对 `project-management` PR 是否具备合并条件做检查。

请检查：
1. OpenSpec artifacts 是否与最终代码一致；
2. review 问题是否都已处理；
3. 当前分支是否只包含本次功能相关改动；
4. 测试和 smoke test 是否具备证据；
5. 合并后是否还需要补充规则、文档或回滚说明。

输出要求：
1. 明确给出“可合并 / 不可合并”；
2. 若不可合并，列出阻塞项；
3. 若可合并，列出合并后仍需执行的动作。
```

### 完成标准

你至少应具备：

1. 独立功能分支；
2. 有验证依据的 focused commit；
3. 真实可审查的 PR 描述；
4. 明确的“可合并 / 不可合并”结论；
5. 合并后的收尾动作清单。

## 9. 开发中发现需求遗漏时的变更回写

### 目标

当开发、联调、测试、评审过程中发现需求遗漏、设计假设错误或范围变化时，先更新当前 change，再继续开发。

### 什么时候触发

出现以下任一情况时，不能直接“顺手改代码”，而应进入变更回写：

1. 当前 `spec.md` 没有覆盖真实业务要求；
2. 前后端对同一 requirement 的理解不一致；
3. RP、接口、字段、导出规则等在联调时发现有遗漏；
4. 当前 design 决策与历史系统真实约束冲突；
5. 当前 tasks 无法覆盖新发现的验证、回归或发布动作。

### 提示词

```text
我们在当前 `project-management` change 的开发过程中发现了需求遗漏或范围细化，请先不要直接修改代码。

请先分析：
1. 这是新 requirement、requirement 细化、设计变更，还是任务补充；
2. 它是否仍然属于当前 `project-management` change；
3. 它会影响 proposal、spec、design、tasks 中的哪些部分；
4. 它会影响前端、后端、联调、测试、发布中的哪些环节；
5. 当前已经完成的实现中，哪些地方需要回归验证。

然后请继续输出：
1. 应更新的 OpenSpec artifacts 清单；
2. 应同步调整的实施计划；
3. 应同步调整的功能验收矩阵；
4. 如果留在当前 change 中，说明为什么可以留；
5. 如果不应留在当前 change 中，明确建议拆新 change。
```

### 回写顺序

推荐固定为：

1. 先做影响分析；
2. 再判断留在当前 change 还是拆新 change；
3. 再更新 `proposal.md` / `spec.md` / `design.md` / `tasks.md`；
4. 再更新实施计划；
5. 再更新功能验收矩阵；
6. 最后再继续编码、联调和验证。

### 完成标准

只有满足下面条件，才算回写完成：

1. 变更已经体现在 OpenSpec artifacts 中；
2. 实施计划已同步；
3. 验收矩阵已同步；
4. 已明确哪些旧实现需要回归验证；
5. 团队可以基于更新后的 change 继续推进，而不是继续依赖口头说明。

## 10. 第 13 步：最终验证

### 目标

在上线前做最后一次证据式确认。

### 提示词

```text
请基于当前项目规则基线和 `project-management` 的 OpenSpec change，对当前实现做最终验证。

验证重点：
1. Completeness：tasks 和 requirements 是否完整覆盖；
2. Correctness：实现是否符合每个 scenario；
3. Coherence：实现是否符合 design 和项目规则基线；
4. Compatibility：旧页面、旧接口、旧链路是否有证据证明未被破坏；
5. Release readiness：是否具备 migration、smoke test、监控、回滚条件。

输出要求：
1. 使用 CRITICAL / WARNING / SUGGESTION 分类；
2. 每个问题都给整改建议；
3. 如果满足上线条件，只能输出“建议进入发布评审”及依据；
4. 依据中必须同时给出：
   - `Change / Commit / PR`
   - 关键测试或验证证据位置
   - 环境
   - 剩余风险
   - 仍需谁确认
5. 明确说明“建议进入发布评审”不等于已批准上线。
```

## 14. 最关键的使用原则

前 1-6 步产出的规则基线不是“前置文档”，而是从第 7 步开始持续生效的开发约束。

所以从第 7 步开始，你每个提示词都要默认带上这句话：

> 请基于当前项目规则基线执行，不要按绿地项目方式重做。

如果中途发现：

1. 规则不够用了；
2. 历史逻辑与你之前抽取的基线不一致；
3. 现有 spec 假设错了；

不要跳过，正确做法是：

1. 先补规则；
2. 再补 OpenSpec；
3. 再同步实施计划和验收矩阵；
4. 再继续开发。
