# 棕地项目规则基线建立手册

> 目标：在接手一个不了解的历史项目后，先通过结构巡查和约定抽取，建立一套“项目统一规则基线”，再在后续 `OpenSpec + Superpowers` 设计、开发、测试、发布中复用这套基线，减少 AI 在棕地项目中“按通用最佳实践乱改”的风险。

---

## 1. 为什么先做规则基线

棕地项目里，AI 最容易犯的错误不是不会写代码，而是：

1. 按自己熟悉的技术栈重组目录；
2. 忽略历史项目里的返回体、异常、权限、租户、审计等隐式约定；
3. 前端改出一套和现有系统完全不同的页面与交互；
4. 测试只验证新功能，不验证旧链路回归。

所以在正式做需求、规格、设计和实现前，要先建立一份“规则基线”。

这份基线不是空泛的编码规范，而是从当前项目中抽取出来的真实约束。

---

## 2. 规则基线的最终形态

建议最终产出三层：

1. **巡查摘要**：当前项目结构、模式、约束、风险的文字总结；
2. **规则文档**：团队共享的前后端基线说明；
3. **AI 规则文件**：写入 `.cursor/rules/`，供后续 AI 会话自动加载或参考。

推荐对应关系：

| 层级 | 产物 | 作用 |
|---|---|---|
| 巡查层 | `execution/BROWNFIELD-RULE-BASELINE-PLAYBOOK.md` | 说明如何从项目现状抽取基线 |
| 说明层 | `execution/BROWNFIELD-AI-PROMPT-HANDBOOK.md` | 说明如何在不同阶段写提示词 |
| 执行层 | `.cursor/rules/*.mdc` | 让 AI 在后续任务里持续遵循规则 |

---

## 3. 第一步：巡查当前项目结构

先不要写规则。先收集证据。

## 3.1 巡查目标

至少回答下面 8 个问题：

1. 后端主技术栈是什么？
2. 前端主技术栈是什么？
3. 目录结构如何分层？
4. Controller / Service / Repository / DTO / Entity 是怎么组织的？
5. 测试目录和测试风格是什么？
6. 返回体、异常、安全、租户、审计有哪些统一模式？
7. 前端页面、组件、API 封装、状态管理、样式体系是什么？
8. 数据库迁移与发布方式是什么？

## 3.2 当前仓库可观察到的后端事实

基于本仓库巡查，可以提炼出一些真实模式。  
注意：下面内容是当前仓库在本次巡查时的**观察快照**，后续如果仓库升级，必须重新核对，不能把这部分当成永远不变的“绝对真相”。

1. 后端是 `Java 17 + Spring Boot 3.2.3 + Maven`；
2. 使用 `MyBatis-Plus`、`PageHelper`、`Redis`、`Validation`；
3. 代码主目录是 `src/main/java/com/lscharge/...`；
4. 测试目录是 `src/test/java/...`；
5. 存在明显的 `Controller / Service / ServiceImpl / Mapper / Model` 结构；
6. 存在 `Response`、`ServiceException`、`TenantContext` 等统一约定；
7. 存在安全加固与过滤器测试，例如 `GlobalParamHandlerFilter`；
8. 测试风格包含 `JUnit 5 + Mockito + ReflectionTestUtils`。

## 3.3 巡查结果怎么记录

建议形成固定结构：

```md
## 项目基线巡查摘要

### Backend Stack
- Java 17
- Spring Boot 3.x
- Maven
- MyBatis-Plus

### Backend Patterns
- Controller / Service / Mapper 分层
- 统一返回体 `Response`
- 业务异常 `ServiceException`
- 存在租户上下文 `TenantContext`

### Testing Patterns
- JUnit 5
- Mockito
- ReflectionTestUtils

### Frontend Patterns
- [若前端仓库已知，在此填写]

### Risks
- 历史服务类较大，修改前需先确认调用面
- 多处能力可能带租户/权限逻辑
```

## 3.4 巡查输出必须证据化

巡查结果不能只有结论，没有证据。  
至少要做到：

1. 每条关键结论附一个真实文件路径；
2. 对核心链路至少给出一条调用链或依赖链；
3. 对不确定结论明确标 `待确认`；
4. 区分“已证实”与“推测”。

### 推荐证据模板

```md
## 巡查证据卡

### 结论
- 项目列表查询链路复用现有分页与统一返回体

### 证据
- Controller: `src/main/java/.../ProjectController.java`
- Service: `src/main/java/.../ProjectServiceImpl.java`
- Mapper: `src/main/java/.../ProjectMapper.java`

### 调用链
- `ProjectPage` -> `projectApi.getList` -> `ProjectController.list` -> `ProjectService.queryPage`

### 风险
- 查询条件里若新增负责人字段，可能牵动旧主数据服务

### 结论状态
- 已证实 / 待确认
```

## 4. 第二步：把巡查结果抽成“规则条目”

从巡查结果里，不是所有信息都要变规则。只抽“会反复影响 AI 行为”的条目。

## 4.1 后端常见规则条目

1. 保持现有分层，不做无关重构；
2. 统一返回体和异常风格必须沿用；
3. 任何新增接口都要先确认权限/租户/审计逻辑；
4. 优先复用现有 Mapper / Service 模式；
5. 测试要覆盖关键业务路径和兼容性回归；
6. migration 要沿用现有命名和执行方式。

## 4.2 前端常见规则条目

1. 优先复用现有路由、布局、组件和 API 封装；
2. 不替换现有组件库和状态管理；
3. 表单校验、弹窗、消息提示统一沿用历史模式；
4. 页面交互要兼容旧行为；
5. 前端验证既要测新功能，也要测旧页面没坏。

## 4.3 项目级常见规则条目

1. 在不了解现状前，不进入实现模式；
2. 先用 OpenSpec 建立规格真相源；
3. 再用 Superpowers 建立执行计划；
4. 所有完成声明必须有验证证据；
5. 发现历史逻辑与 spec 冲突时，先更新 artifacts 再继续。

---

## 5. 第三步：把规则条目写成可执行基线

推荐拆成三类规则：

1. **项目级规则**：始终生效；
2. **后端规则**：只对 Java 文件生效；
3. **前端规则**：只对 Vue / React / TS / JS 文件生效。

这样做的好处是：

1. 不会把所有要求写成一坨；
2. AI 打开具体文件时，会加载对应上下文；
3. 项目级规则负责流程，语言级规则负责实现。

---

## 6. 第四步：如何在后续阶段复用这套基线

## 6.1 需求澄清阶段

把规则基线当成“提问边界”：

- 问题必须围绕兼容性、边界和约束；
- 不允许还没了解现状就问“要不要重构”。

### 提示词模板

```text
请基于当前项目规则基线进行需求澄清。

要求：
1. 把历史项目约束视为前提；
2. 优先问兼容性、受影响链路、非目标和发布方式；
3. 不要脱离现有项目模式设计新架构；
4. 输出结果必须能直接进入 OpenSpec。
```

## 6.2 OpenSpec 阶段

把规则基线当成“规格约束”：

- `proposal` 要写清对旧系统的影响；
- `spec` 要有兼容场景；
- `design` 要写复用边界和回滚点；
- `tasks` 要包含调研、回归和发布准备。

### 提示词模板

```text
请基于当前项目规则基线生成 OpenSpec artifacts。

要求：
1. proposal 必须写受影响的旧链路；
2. spec 必须包含兼容性场景；
3. design 必须说明复用哪些现有模块；
4. tasks 必须包含回归验证和发布准备；
5. 不要按绿地项目思路全量重做。
```

## 6.3 设计与开发阶段

把规则基线当成“实现约束”：

- 后端先说明复用哪些旧模块；
- 前端先说明复用哪些旧页面/组件/API；
- 不允许无关重构；
- 若有不确定逻辑，先列待确认。

### 后端提示词模板

```text
请基于当前项目规则基线实现后端任务。

要求：
1. 遵循现有 Controller / Service / Mapper 分层；
2. 沿用统一返回体、异常处理、租户/权限逻辑；
3. 不要做无关重构；
4. 先说明将复用哪些现有模块和风险点，再给实现方案。
```

### 前端提示词模板

```text
请基于当前项目规则基线实现前端任务。

要求：
1. 复用现有页面结构、组件模式、API 封装、校验和消息提示；
2. 不替换组件库和状态管理；
3. 兼容旧页面交互；
4. 先说明要复用哪些页面和组件，再给实现方案。
```

## 6.4 测试与验证阶段

把规则基线当成“验收标准”：

- 不只测新增功能；
- 必须测旧链路没坏；
- 验证结果必须能支撑归档和发布。

### 提示词模板

```text
请基于当前项目规则基线做验证。

要求：
1. 同时检查新功能和旧链路兼容性；
2. 输出测试证据、风险点和是否满足发布条件；
3. 若发现现状与规则基线冲突，指出需要更新的规则或 spec。
```

---

## 7. 第五步：实战中的标准工作流

这是最推荐的一条线：

1. 巡查项目结构和约定；
2. 产出带证据的“项目基线巡查摘要”；
3. 抽取规则条目；
4. 写入 `.cursor/rules/`；
5. 用规则基线约束 `brainstorming`；
6. 用规则基线约束 `OpenSpec`；
7. 用规则基线约束 `writing-plans`；
8. 用规则基线约束前后端实现；
9. 用规则基线约束测试、验证、归档。

如果中途发现规则不完整，不要靠实现阶段“临场修正”，而是：

1. 补规则；
2. 补 OpenSpec；
3. 再继续开发。

---

## 8. 给团队的统一开场提示词

```text
请先不要直接设计或实现功能。先基于当前历史项目做结构巡查，并生成一套项目统一规则基线。

你需要完成：
1. 总结后端技术栈、分层、异常、权限、租户、测试模式；
2. 总结前端路由、页面、组件、API 封装、状态管理、测试模式；
3. 抽取出会反复影响 AI 开发行为的规则条目；
4. 把这些规则分成项目级、后端级、前端级三层；
5. 给出后续需求、OpenSpec、设计、开发、测试阶段可直接复用的提示词模板。

要求：
1. 不要假设这是新项目；
2. 不要一上来给重构方案；
3. 先描述现状，再提炼规则，再输出提示词；
4. 输出结果要能直接用于 OpenSpec + Superpowers 工作流。
```

---

## 9. 最终口径

棕地项目里最重要的不是“让 AI 更聪明”，而是“让 AI 先受约束，再开始发挥”。

你的统一方法应该是：

1. 先巡查；
2. 再抽规则；
3. 再固化为基线；
4. 再让 OpenSpec 和 Superpowers 在这套基线上工作。

一句话总结：

> 巡查项目现状是为了发现约束，规则基线是为了固化约束，后续提示词是为了让 AI 持续遵守这些约束。
