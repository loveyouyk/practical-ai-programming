# AI 编程落地效果度量指南

> 目标：为团队推广 AI 编程落地方案后提供一套可执行的度量机制，回答"做得好不好怎么衡量"。  
> 使用场景：推广试点后进行效果评估、季度复盘、持续优化依据。  
> 使用边界：度量是为了改进而不是考核，不建议在推广初期用于个人 KPI 评定。

---

## 1. 为什么需要度量

推广一段时间后，管理者需要回答：

1. 这套方法到底有没有提效？
2. 哪些环节执行得好、哪些被跳过了？
3. AI 辅助的需求和非 AI 辅助的需求相比，质量和效率差异如何？
4. 规则基线是否在持续生效？
5. 证据门禁是否流于形式？

如果不度量，推广就只能靠"感觉"来判断成败。

---

## 2. 度量框架总览

建议从五个维度进行度量：

| 维度 | 核心问题 | 度量频率 |
|---|---|---|
| 流程遵从度 | 团队是否按正确路径执行 | 每个迭代 |
| 证据完整度 | 结构化证据是否真正落地 | 每次 PR |
| 规则基线健康度 | 规则是否在持续生效和更新 | 每月 |
| 质量对比 | AI 辅助 vs 非 AI 辅助的质量差异 | 每季度 |
| 团队接受度 | 团队是否愿意持续使用 | 每季度 |

---

## 3. 流程遵从度指标

### 3.1 分流准确率

```
定义：需求实际走的路径与应走路径一致的比例
公式：正确分流的需求数 / 总需求数 × 100%
目标值：≥ 85%
采集方式：每个需求在 PR 描述中标注实际路径（S/M/L），由 TL 复盘时核对
```

### 3.2 路径执行完整率

```
定义：按对应路径要求完成所有必要步骤的比例
```

| 路径 | 必要步骤 | 完整率计算 |
|---|---|---|
| S-Low | 规则加载 + 最小验证证据 + PR | 完成步骤数 / 2 |
| M-Medium | 最小探索 + 最小 OpenSpec + 审批 + 验收矩阵 + 证据 | 完成步骤数 / 5 |
| L-High Risk | 完整探索 + 完整 OpenSpec + 计划 + 多角色开发 + 验收 + 交付模板 + 发布门禁 | 完成步骤数 / 7 |

### 3.3 硬性升级条件命中率

```
定义：命中硬性升级条件但仍走了轻流程的需求比例
目标值：0%（不允许）
采集方式：复盘时核查涉及权限/租户/导出语义/旧接口契约/事务边界的需求是否误走 S-Low
```

---

## 4. 证据完整度指标

### 4.1 结构化证据块填写率

```
定义：PR 中包含完整结构化证据块的比例
完整定义：至少包含 Change/Commit/PR、Command、Environment、Result、Conclusion、Residual Risk
```

| 路径 | 目标填写率 |
|---|---|
| S-Low | ≥ 60%（至少保留关键验证动作和结果） |
| M-Medium | ≥ 90% |
| L-High Risk | 100% |

### 4.2 验收矩阵闭环率

```
定义：验收矩阵中 requirement 从"未开始"推进到"验证通过"的比例
公式：验证通过的 requirement 数 / 总 requirement 数 × 100%
目标值：M 级 ≥ 90%，L 级 100%
```

### 4.3 证据有效性

```
定义：Reviewer 判定证据"真实且足够支撑结论"的比例
采集方式：Reviewer 在 PR review 中标注证据是否有效
目标值：≥ 85%
```

---

## 5. 规则基线健康度指标

### 5.1 规则更新频率

```
定义：.cursor/rules/*.mdc 每月被有效更新的次数
目标值：≥ 1 次/月（在有高风险需求完成的月份）
采集方式：统计 rules 文件的 commit 频率
```

### 5.2 规则反馈处理速度

```
定义：一线开发提交 rule conflict/gap/outdated 反馈后，到 owner 响应的平均时间
目标值：≤ 3 个工作日
采集方式：跟踪 rule feedback issue 或 PR 的响应时间
```

### 5.3 规则覆盖度

```
定义：规则基线是否覆盖团队当前最常用的技术模式
采集方式：每季度让一线开发填写"过去一季度是否遇到规则未覆盖的场景"
目标值：未覆盖场景报告 ≤ 3 条/季度
```

---

## 6. 质量对比指标

### 6.1 上线后缺陷密度对比

```
定义：AI 辅助开发的需求 vs 非 AI 辅助开发的需求，上线后单位时间内的缺陷数
公式：缺陷数 / 功能点数
采集方式：按需求标签区分 AI 辅助/非 AI 辅助，统计上线后 2 周内的 bug 数
目标值：AI 辅助 ≤ 非 AI 辅助（至少不劣于）
```

### 6.2 兼容性回归问题率

```
定义：上线后因兼容性问题导致的回滚或紧急修复次数
公式：兼容性相关回滚次数 / 总发布次数 × 100%
目标值：≤ 5%
```

### 6.3 需求变更回写及时率

```
定义：开发中发现需求遗漏后，先回写 OpenSpec 再继续开发的比例
公式：先回写再继续的次数 / 总遗漏发现次数 × 100%
目标值：≥ 80%
```

### 7.2 NPS（净推荐值）简化版

```
问题：你有多大可能向其他团队推荐这套 AI 编程方法？（1-10 分）
NPS = (9-10 分人数 - 1-6 分人数) / 总人数 × 100%
目标值：≥ 30
```

## 8. 度量节奏建议

| 频率 | 度量动作 |
|---|---|
| 每次 PR | Reviewer 标注证据有效性 |
| 每个迭代 | TL 核查分流准确率、路径执行完整率 |
| 每月 | 统计规则更新频率、反馈处理速度 |
| 每季度 | 质量对比、团队接受度调查、NPS 统计、规则覆盖度复盘 |
| 每半年 | 全面复盘，决定方法体系是否需要调整 |

## 10. 推广阶段度量重点

不同推广阶段关注不同指标：

### Phase 1（建立共识阶段）

重点看：
1. 团队是否理解三条路径
2. 团队是否认同三条铁律
3. 采集方式：口头/问卷确认

### Phase 2（M 级试点阶段）

重点看：
1. M 级路径执行完整率
2. 审批耗时是否在 SLA 内
3. 证据填写率
4. 团队反馈（摩擦点在哪里）

### Phase 3（L 级试点阶段）

重点看：
1. L 级路径执行完整率
2. 验收矩阵闭环率
3. 兼容性回归问题率
4. 上线后缺陷密度

### Phase 4（全面推广阶段）

重点看：
1. 分流准确率
2. 质量对比数据
3. 规则基线健康度
4. NPS

---

## 11. 度量注意事项

1. **度量是为了改进，不是为了考核** — 推广初期的数据波动是正常的，不要用它惩罚团队
2. **度量不要太重** — 初期只采集最核心的 3-5 个指标，不要一次性上全部指标
3. **度量要可信** — 数据采集方式必须简单且可持续，靠人工填的指标很容易失真
4. **度量要有闭环** — 每次度量后必须输出至少 1 条改进行动项，否则度量就变成了形式
5. **度量口径要统一** — 全团队对"AI 辅助开发"的定义、对"缺陷"的定义必须一致

---

## 12. 一句话总结

> 推广落地的效果好不好，不能只靠感觉，必须靠数据；但度量的目的是改进方法，而不是给人贴标签。
