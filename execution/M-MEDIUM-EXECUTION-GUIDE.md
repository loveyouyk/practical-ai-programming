# M-Medium 快车道执行指南

> 目标：给 M 级需求一份**端到端的独立执行手册**，从分流判断到验收结束，一份文档走完，不需要在多份 L 级文档中拼凑。  
> 适用范围：标准 CRUD、独立页面新增、标准 API 对接、边界清晰的功能增强。  
> 使用前提：已完成治理分流判断（`core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`），确认当前需求属于 M-Medium。  
> 升级条件：如果执行中发现边界不清 / 主数据来源不清 / 旧链路影响超预期 / 风险高于原判断，应升级到 L 级完整流程。

---

## 1. M 级全流程总览

```
分流判断 → 最小探索（含 QUIRK 登记）→ 最小 OpenSpec → 快速审批 → 开发（前后端交叉）→ 验收矩阵 → 结构化证据 → PR → 完成
```

与 L 级的关键差异：

| 维度 | M-Medium | L / High Risk |
|---|---|---|
| 探索深度 | 最小探索（聚焦复用点和 QUIRK） | 完整探索 |
| 巡查/规则/固化 | 合并为一步 | 三步串行 |
| OpenSpec 强度 | 最小骨架（参考 `M-MEDIUM-MINIMAL-OPENSPEC-EXAMPLE.md`） | 完整四件套 |
| 审批方式 | 快速审批（≤4h，支持微调后通过） | 多角色正式审批 |
| 开发节奏 | 后端骨架→前端骨架→联调填充（交叉迭代） | 后端完成→前端完成→联调 |
| 验收矩阵 | 精简版（7 列） | 完整版（11 列） |
| 证据强度 | 精简证据（4 字段） | 完整证据（7 字段） |
| 实施计划 | 可选（复杂 M 级补） | 必须 |
| 交付模板 | 可选 | 必须 |

---

## 2. 第一步：最小探索（含 QUIRK 登记）

M 级的巡查、规则提炼、固化三步合并为一步执行。

### 提示词

```text
请进入棕地项目探索模式。我要在这个历史项目中新增"[模块名称]"，功能包括：
1. [功能 1]
2. [功能 2]
3. [功能 3]

请输出：
1. 【复用点】可以直接复用的前后端模块、组件、服务
2. 【约束】必须遵守的统一返回体、异常处理、租户机制、分页、导出等约定
3. 【QUIRK】发现的历史怪癖（组件非直觉行为、数据约定不一致等），格式：组件/服务 + QUIRK 描述 + 正确应对方式
4. 【数据翻译约定】字段翻译由前端还是后端完成？日期格式化由谁做？
5. 【待确认】不确定的项，标记为"待确认"
6. 每条关键结论附真实文件路径

不要设计新功能，不要写代码。
```

### 完成标准

你已拿到：
1. 复用点清单
2. 约束清单（可直接嵌入后续提示词）
3. QUIRK 登记簿
4. 数据翻译约定
5. 待确认项清单

---

## 3. 第二步：最小 OpenSpec

### 如何把探索结果喂给 OpenSpec 生成

**关键衔接动作：** 把上一步的"约束清单"和"待确认项"手动嵌入到 OpenSpec 生成提示词中。不要依赖 AI "记住"上一轮对话。

### 提示词

```text
这是一个 M 级棕地需求。请基于以下约束生成最小 OpenSpec change。

【已知约束】（从探索结果搬运过来）
1. [约束 1]
2. [约束 2]
3. [约束 3]
...

【待确认项】（从探索结果搬运过来）
1. [待确认 1]
2. [待确认 2]

请生成 proposal / spec / design / tasks 四份文档：
1. proposal 写清范围、非目标、影响面
2. spec 使用 ADDED Requirements，每个 requirement 至少 1 个正常场景 + 1 个异常/兼容场景
3. design 写清 API 契约（字段级）、数据模型、复用方式。严禁包含与数据翻译约定不一致的字段
4. tasks 按 Discovery → Backend → Frontend → Verification 分组
5. 在 design 末尾增加 Pending Confirmations 节，列出所有待确认项

生成后停下，等待人工审批。

骨架参考：execution/M-MEDIUM-MINIMAL-OPENSPEC-EXAMPLE.md
```

如果 `@openspec-ff-change` 可用，可替代上述提示词直接生成。不可用时按上述方式手动生成。

### 完成标准

四份文档齐全，待确认项显式标出。

---

## 4. 第三步：快速审批

### 审批 SLA

- 响应时间：≤ 4 小时
- 最多修改轮次：2 轮（超过则升级为 L 级）
- 条件性开始：超时未响应可先推进低风险部分

### 审批 Checklist

```md
### proposal
- [ ] 范围和非目标是否明确
- [ ] 是否存在应升级为 L 级的隐藏风险

### spec
- [ ] requirement 是否覆盖所有已知功能点
- [ ] 是否有异常场景（校验失败、编号重复等）
- [ ] 是否有兼容性 scenario

### design
- [ ] 接口字段是否与现有模式一致
- [ ] 字段翻译约定是否符合历史惯例
- [ ] 待确认项是否显式标出

### tasks
- [ ] 是否包含验证项
- [ ] 是否包含"确认待确认项"的任务
```

### 审批结果

三种之一：
1. **通过** → 进入开发
2. **微调后通过** → TL 指出修改点，补充后无需再审
3. **不通过** → 方向错误或应升级为 L 级

## 5. 第四步：开发（交叉迭代）

M 级不要求严格"先后端再前端"。推荐节奏：

```
后端骨架（Controller/Service/表结构）
  ↓↑ 同步对齐查询参数和响应字段
前端骨架（页面/路由/API 封装）
  ↓
联调填充（逐个功能点前后端联通）
```

### 后端提示词

```text
你现在在一个历史 Java 项目中新增 [模块名称]。严格遵守现有项目规范。

已知约束：
[从探索结果搬运]

QUIRK 警告：
[从 QUIRK 登记簿搬运]

严禁：
- 使用 ResponseEntity（必须用 Response<T>）
- 返回 xxxName 翻译字段（本项目由前端翻译）
- 做无关重构

请先输出你理解的现有模式和风险点，再给出实现方案。
```

### 前端提示词

```text
你现在在一个历史前端项目中新增 [模块名称] 页面。优先复用现有模式。

已知约束：
[从探索结果搬运]

QUIRK 警告（必须逐条处理）：
- SearchForm：重置不自动搜索 → 在 @reset 中手动查询
- BaseTable：默认 pageSize=20 → 查询参数对齐
- FormDialog：confirm 不关闭 → API 成功后手动关闭
- DictService：key 是 String → 注意类型转换
[从 QUIRK 登记簿搬运]

请先列出你注意到的 QUIRK 及应对方式，再给出实现方案。
```

### 变更回写

开发中（或审批中）发现与 spec/design 不一致时：

```text
发现以下不一致：[具体描述]

请先分析这是 requirement 变化、设计变更还是任务补充。
然后给出需要更新的 OpenSpec 文档清单和具体修改内容。
不要直接改代码。
```

## 6. 第五步：验收矩阵（M 级精简版）

### 矩阵模板（7 列）

```md
| Requirement | Scenario | 实现状态 | 联调验证 | 证据 | 状态 | 备注 |
|---|---|---|---|---|---|---|
```

### 提示词

```text
请基于 [模块名称] 的 OpenSpec change 输出 M 级精简验收矩阵（7 列）。

requirement 清单：
1. [Requirement 1]
2. [Requirement 2]
...

没有证据的项不能标记为通过。最后给出"部分达标 / 建议进入发布评审"结论。
```

---

## 7. 第六步：结构化证据（M 级精简版）

### 精简证据模板（4 字段）

```md
## Verification Evidence

### What（做了什么）
- Commit: [hash]
- 操作：[具体步骤]

### Result（结果是什么）
- [可观察的具体结果]

### Conclusion（结论）
- [通过/未通过 + 理由]

### Residual Risk（剩余风险）
- [未覆盖的场景]
```

与完整版（7 字段）的关系：M 级用 4 字段精简版即可。如果需求后续升级为 L 级，再补齐 Environment / Evidence Location / Change-PR 关联。

---

## 8. 第七步：PR 与完成

```text
请基于 [模块名称] 的 OpenSpec change，帮我准备 PR 描述。

请输出：
1. 做了什么
2. 没做什么
3. 哪些旧链路被保护
4. 验证了什么
5. 剩余风险
```

### M 级完成定义

同时满足以下条件，M 级需求算完成：

1. OpenSpec 四件套齐全（含待确认项标注）
2. 审批已通过（含微调）
3. 代码实现与 spec/design 一致
4. 验收矩阵每条 requirement 有证据
5. QUIRK 登记簿已更新（如有新发现）
6. PR 已提交
