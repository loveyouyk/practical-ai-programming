# 棕地项目实战案例：项目管理模块

> 案例目标：用一个更接近真实企业业务的功能模块，演示如何在棕地项目中使用 `opsx-explore + 规则基线 + OpenSpec + Superpowers + Git/PR/Merge + 交付模板` 完成一次新增功能交付。  
> 适用场景：历史项目中新增“项目管理”功能，能力包括 `列表查询`、`新增`、`修改`、`导出`，并可能存在 RP 原型链接或现成 UI 设计稿。

在使用本案例前，建议先补看：

- `core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`

如果你不确定当前环境能否直接使用 `/opsx-*` 或 Superpowers，请先补看：

- `execution/AI-WORKFLOW-TOOLING-PREREQUISITES.md`

---

## 1. 为什么用这个案例

简单待办类案例适合教学，但真实企业里更常见的是这种模块：

1. 有列表页；
2. 有复杂查询条件；
3. 有新增和编辑表单；
4. 有导出；
5. 有权限、租户、字典、枚举、导出模板等历史依赖；
6. 往往还有 RP 原型、设计稿或产品文档。

这种案例更能反映棕地项目里真实的复杂度。

这里也要明确：

1. 这个案例主要用于演示完整方法如何落地；
2. 它默认更接近 `L / High Risk` 场景；
3. 不建议把所有日常需求都直接套成这个案例的完整流程强度。

---

## 2. 案例背景设定

假设你接手的是一个已经上线多年的业务后台系统，现在产品提出新增“项目管理”模块。

### 业务方给出的需求通常像这样

1. 新增一个“项目管理”菜单；
2. 支持列表查询；
3. 支持按项目名称、项目编号、项目状态、负责人、创建时间筛选；
4. 支持新增项目；
5. 支持修改项目；
6. 支持导出当前筛选结果；
7. 列表和表单 UI 已经在 RP 中设计好；
8. 必须复用现有权限、租户、导出、字典、日志体系。

### 这类需求在棕地项目里的真实风险

1. 系统里可能已经有“项目”“组织”“客户”“合同”之类相近模块；
2. 项目状态可能有历史字典或历史枚举；
3. 导出可能必须复用统一导出组件或后端导出工具；
4. 菜单权限、按钮权限、租户隔离不能漏；
5. RP 原型不一定等于真实可落地实现，需要和现有页面模式对齐；
6. 列表字段、查询条件、导出字段可能涉及多个旧表拼接。

这里要特别强调：

1. RP 只能帮助你理解可见交互；
2. 业务语义、字段来源、权限范围、导出规则仍然要以代码、文档、业务确认和验证证据为准。

## 3. 这个案例中，为什么必须先 `opsx-explore`

这里不是“因为有人建议”，而是因为这个功能天然具有棕地项目典型复杂性：

1. 你无法只靠需求描述判断系统里有没有类似模块；
2. 你无法只看 UI 原型判断后端表结构怎么落；
3. 你无法只看页面字段判断权限、导出、字典、租户逻辑是否已存在；
4. 你如果不先 explore，很容易直接写出一套“看起来合理的新模块”，但和历史系统实际约束不一致。

所以，这个案例里 `opsx-explore` 不是装饰，而是非常合理的第一步。

## 3.1 这个案例在治理层里的默认分级

按：

- `core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`

的口径，这个主案例默认更适合作为 `L / High Risk` 示例，而不是 `S-Low` 或通用默认路径。  
原因不是功能名字“大”，而是它天然同时触及：

1. 权限；
2. 租户；
3. 导出语义；
4. 主数据来源；
5. 旧页面、旧接口和旧导出链路兼容。

也就是说：

> 本案例适合拿来解释“为什么完整流程有价值”，但不适合被误用成“所有需求都必须这样走”。

## 3.2 如果把需求缩成 `M-Medium`，应该怎么走

如果实际需求被收敛成：

1. 只增加一个独立页面；
2. 不改权限模型；
3. 不改租户或数据范围逻辑；
4. 不改导出语义；
5. 主数据来源和接口边界都比较清晰；

那么更合适的走法是：

1. 最小探索；
2. 最小 OpenSpec；
3. 快速审批；
4. 审批通过后开发；
5. 保留验收矩阵和结构化证据。

只有在实施中发现：

1. 边界不清；
2. 主数据来源不清；
3. 旧链路影响超预期；
4. 验证项明显不足；

时，再升级回完整流程。

## 4. 第一步：用 `opsx-explore` 先摸清现状

### 你此时掌握的输入

通常只有这些：

1. 一个业务需求描述；
2. 一个 RP 原型链接；
3. 一个模块名称；
4. 零散的字段说明。

### 你此时不要做的事

1. 不要直接设计数据库表；
2. 不要直接生成 Controller / Service / Mapper；
3. 不要直接写 Vue / React 页面；
4. 不要直接写 OpenSpec。

### 推荐提示词

```text
请先进入棕地项目探索模式，不要设计新功能，也不要写代码。我要在这个历史项目中新增“项目管理”模块，功能包括：
1. 列表查询
2. 新增
3. 修改
4. 导出

补充上下文：
- 如果系统里已有 RP 原型或设计稿，请把它视为 UI 输入，而不是实现方案
- 当前项目是棕地项目，必须优先识别现有复用关系和兼容约束

请重点找出：
1. 系统里是否已有相近模块，如项目、客户、合同、组织、字典、导出能力；
2. 前端相关页面入口、路由、共享表格、共享表单、共享导出组件；
3. 后端相关 Controller、Service、Mapper、表结构、导出工具、权限和租户逻辑；
4. 项目状态、负责人、客户等字段是否已有字典或主数据来源；
5. 列表查询、新增、修改、导出分别最可能复用哪些旧模块；
6. 本次新增最可能破坏哪些旧链路；
7. 还缺哪些信息必须向产品或业务确认。

输出要求：
1. 先输出“现状地图”；
2. 再输出“复用候选点”；
3. 再输出“高风险点”；
4. 最后输出“待确认问题”；
5. 每条关键结论至少附一个真实文件路径；
6. 至少给出一条页面到接口链、调用链或依赖链；
7. 不确定项明确标记为 `待确认`；
8. 不给实现代码。
```

### 你应该得到的结果

至少应拿到：

1. 前端页面与组件复用地图；
2. 后端服务与表结构复用地图；
3. 导出能力和权限能力是否已有；
4. 项目状态、负责人等字段的真实来源；
5. 风险清单与待确认问题；
6. 关键结论对应的真实文件路径证据；
7. 至少一条关键调用链证据。

## 5. 第二步：把探索结果提炼成规则基线

这个案例里，规则基线不是通用“代码规范”，而是围绕“项目管理模块”本次需求实际相关的约束。

### 应重点提炼的规则

#### 项目级规则

1. 项目管理模块必须复用现有权限体系；
2. 项目管理模块必须复用现有导出能力；
3. 所有新增能力都要遵循租户隔离；
4. RP 原型只作为 UI 输入，不能绕过现有前端模式；
5. 未确认主数据来源前，不允许拍脑袋新增字段语义。

#### 后端规则

1. 列表查询必须沿用现有分页、筛选和返回体模式；
2. 新增与修改必须接入现有校验和异常处理；
3. 导出必须复用现有导出服务或工具，不得另造一套；
4. 状态、负责人、客户等字段优先复用现有字典或主数据来源；
5. 涉及租户字段时必须确认查询和导出都遵守租户过滤。

#### 前端规则

1. 列表页必须复用现有列表页结构和表格组件；
2. 查询区必须复用现有表单、筛选、重置模式；
3. 新增和修改优先复用同一表单弹窗/抽屉模式；
4. 导出按钮必须沿用已有交互和 loading 反馈；
5. 页面不能因为 RP 原型更美观就绕开现有设计系统。

### 提示词

```text
请基于刚才对“项目管理模块”的探索结果，提炼本次功能最需要固化的规则基线。

请分三层输出：
1. 项目级规则；
2. 后端规则；
3. 前端规则。

要求：
1. 每条规则都必须来自当前项目真实现状；
2. 规则要能够约束后续 AI 设计与实现行为；
3. 规则要优先覆盖：
   - 权限
   - 租户
   - 导出
   - 主数据来源
   - 前端页面与组件复用
4. 不要输出空泛最佳实践。
```

## 6. 第三步：需求澄清

现在才开始真正澄清需求。

### 这类案例要问的关键问题

1. 列表查询字段到底有哪些；
2. 导出字段和列表字段是否一致；
3. 新增和修改字段是否一致；
4. 项目状态是否固定枚举；
5. 负责人、客户、组织是否来自已有主数据；
6. 是否需要删除、详情、查看日志；
7. 是否需要按钮级权限控制；
8. 导出是否按当前筛选条件导出。

### 提示词

```text
请基于当前项目规则基线，帮助我澄清棕地项目中的“项目管理”模块需求。

当前已知功能：
1. 列表查询
2. 新增
3. 修改
4. 导出

请一次只问一个关键问题，优先问：
1. 列表查询条件；
2. 列表展示字段；
3. 表单字段；
4. 导出范围；
5. 权限与租户要求；
6. 必须兼容的旧行为；
7. 非目标；
8. 上线和回滚要求。

当信息足够时，请输出：
1. 需求摘要；
2. 当前行为；
3. 目标行为；
4. 必须兼容的旧行为；
5. 风险和回滚点；
6. 待确认问题。
```

## 7. 第四步：进入 OpenSpec

### capability 建议

这个案例里建议 capability 命名为：

- `project-management`

### proposal 提示词

```text
请基于当前项目规则基线和已澄清需求，为棕地项目中的“项目管理”模块新增功能生成 OpenSpec proposal。

功能范围：
1. 列表查询
2. 新增
3. 修改
4. 导出

要求：
1. capability 使用 `project-management`；
2. proposal 必须写清：
   - 为什么做
   - 当前系统的缺口
   - 会复用哪些旧链路
   - 会影响哪些旧页面、旧接口、旧数据结构
   - 非目标
   - 风险和兼容边界
3. 用“在现有系统上增量扩展”的口径写。
```

### spec 提示词

```text
请为 `project-management` 生成功能 spec。

要求：
1. 使用 ADDED Requirements；
2. requirement 至少覆盖：
   - Query Project List
   - Create Project
   - Update Project
   - Export Project List
3. 每个 requirement 都要考虑棕地项目兼容性；
4. 至少补充以下场景：
   - 列表筛选场景
   - 表单校验场景
   - 导出按筛选条件生效场景
   - 旧权限和旧数据来源不被破坏的兼容性场景
   - 租户范围不越界场景
5. requirement 同时覆盖前端体验和后端行为。
```

### design 提示词

```text
请基于当前项目规则基线，为 `project-management` 生成 OpenSpec design。

要求：
1. 后端必须说明：
   - 列表查询链路
   - 新增/修改接口契约
   - 请求/响应字段示例
   - 导出实现复用方式
   - 字典/主数据来源
   - 权限/租户/异常处理
2. 前端必须说明：
   - 列表页入口
   - 查询区
   - 列表表格
   - 新增/修改弹窗或页面
   - 导出按钮和反馈
   - RP 原型如何映射到现有页面模式
3. 如果 API 路径仍是占位表达，必须显式标记后续由探索结果替换；
4. 必须写清兼容策略、验证策略、回滚策略。
```

### tasks 提示词

```text
请基于当前项目规则基线和已有 proposal/spec/design 生成 `project-management` 的 OpenSpec tasks。

要求：
1. 按以下顺序分组：
   - Brownfield Discovery
   - Backend List Query
   - Backend Create/Update
   - Backend Export
   - Frontend List Page
   - Frontend Form
   - Frontend Export
   - Integration
   - Verification
   - Release Preparation
2. 每个任务都要体现兼容性和回归考虑；
3. 任务粒度要适合后续交给 writing-plans 继续展开。
```

## 8. 第五步：进入 Superpowers 实施计划

### 提示词

```text
请基于当前项目规则基线和 `project-management` 的 OpenSpec artifacts 生成实施计划。

要求：
1. 这是棕地项目，不是新项目；
2. 先处理兼容性和现状约束，再处理后端、前端、联调；
3. 每个任务都要明确：
   - 复用哪些旧模块
   - 影响哪些旧链路
   - 需要验证什么
   - 需要保留哪些证据
4. 计划至少拆到：
   - 后端列表查询
   - 后端新增/修改
   - 后端导出
   - 前端列表页
   - 前端查询区
   - 前端新增/修改表单
   - 前端导出按钮
   - 联调与验证
5. 后续执行按 subagent-driven-development 组织。
```

## 9. 第六步：多角色开发

### 后端实现者提示词

```text
你现在扮演棕地项目中的后端实现者，请基于当前项目规则基线和 `project-management` 的 OpenSpec artifacts 实现后端任务。

要求：
1. 严格遵循现有 Controller / Service / Mapper 分层；
2. 列表查询要复用现有分页、筛选、返回体模式；
3. 新增和修改要接入现有校验、异常、权限、租户逻辑；
4. 导出要复用现有导出能力，不允许另造一套；
5. 状态、负责人、客户等字段优先复用现有字典或主数据来源；
6. 先输出：
   - 本次会复用哪些旧模块
   - 会影响哪些旧链路
   - 风险点
7. 再输出实现方案和验证方式；
8. 若发现 design 契约与真实项目路径冲突，先回写 OpenSpec 再继续。
```

### 前端实现者提示词

```text
你现在扮演棕地项目中的前端实现者，请基于当前项目规则基线和 `project-management` 的 OpenSpec artifacts 实现前端任务。

要求：
1. 列表页必须复用现有表格页结构；
2. 查询区必须复用现有筛选表单模式；
3. 新增和修改优先复用同一表单弹窗/抽屉；
4. 导出按钮必须沿用已有导出交互和 loading 反馈；
5. RP 原型只作为 UI 输入，不能绕开现有设计系统；
6. 先输出：
   - 现有页面结构和可复用组件
   - 可能影响的旧页面或公共组件
   - 风险点
7. 再输出实现方案和测试方式；
8. 前后端字段命名或错误提示若与 spec 不一致，先回写 artifacts 再继续。
```

### Spec Reviewer 提示词

```text
你现在扮演 Spec Reviewer，请基于 `project-management` 的 OpenSpec artifacts 和当前项目规则基线，检查当前实现是否符合规格。

检查重点：
1. 是否完整覆盖列表查询、新增、修改、导出四类 requirement；
2. 是否遗漏了兼容性场景；
3. 导出是否真正复用了既有导出规则；
4. 是否破坏了旧权限、旧字典、旧主数据来源；
5. 是否前后端围绕同一个 capability。
```

### Code Quality Reviewer 提示词

```text
你现在扮演 Code Quality Reviewer，请基于当前项目规则基线检查“项目管理模块”改动的质量。

检查重点：
1. 是否遵循现有项目结构和模式；
2. 是否存在无关重构；
3. 列表、表单、导出是否复用了该复用的公共能力；
4. 权限、租户、校验、测试是否完整；
5. 是否存在棕地项目中的高风险兼容性问题。
```

## 10. 第七步：联调、提交、PR、上线

这个案例里，开发完成后不能直接说“做完了”，而要进入真实工程流程。

### 联调与测试提示词

```text
请基于当前项目规则基线，对“项目管理”模块做联调和测试设计。

要求：
1. 同时覆盖：
   - 列表查询
   - 新增
   - 修改
   - 导出
   - 权限 / 租户场景
   - 主数据引用校验场景
   - 旧链路回归
2. 输出关键测试场景、兼容性回归场景、验证步骤和测试证据要求；
3. 显式检查 RP 对应的核心 UI 交互是否落地正确。
```

### 功能验收矩阵提示词

```text
请基于 `project-management` 的 OpenSpec change、当前实现进度、测试结果和联调结果，输出功能验收矩阵。

要求：
1. 每条 requirement 和 scenario 单独映射；
2. 没有证据的项不能标记为通过；
3. 对 `L / High Risk`，证据至少补齐测试结果、联调结果、旧链路回归结果、请求/响应样例、关键证据位置和剩余风险；
4. 最后给出“建议进入发布评审 / 不建议进入发布评审 / 部分达标”的三选一结论；
5. 明确该结论只是基于证据的验收建议，不替代最终人工审批。
```

### Git / Commit / PR 提示词

```text
请基于当前项目规则基线和 `project-management` change，帮我准备 git 提交、代码评审和 PR 合并流程。

请输出：
1. 功能分支命名建议；
2. 当前适合提交哪些 focused commit；
3. 每次 commit 前应完成哪些验证；
4. PR 标题和 PR 描述；
5. PR 合并前必须检查的事项；
6. 合并后还需要补哪些验证和文档动作；
7. 如果当前环境无法直接执行 `/opsx-verify`，明确给出等价人工验证门禁。
```

### 发布准备提示词

```text
请基于当前项目规则基线和 `project-management` 变更，生成发布准备清单。

要求：
1. 同时覆盖后端、前端、数据库；
2. 明确配置项、migration、健康检查、监控项、回滚点；
3. 明确旧链路观察项；
4. 输出结果要能直接作为上线执行清单。
```

### 最终验证提示词

```text
请基于当前项目规则基线和 `project-management` 的 OpenSpec change，对当前实现做最终验证。

验证重点：
1. Completeness
2. Correctness
3. Coherence
4. Compatibility
5. Release readiness

输出要求：
1. 使用 CRITICAL / WARNING / SUGGESTION 分类；
2. 每个问题给整改建议；
3. 如果满足上线条件，只能输出“建议进入发布评审”及依据；
4. 依据中必须给出关键证据位置、环境、剩余风险和仍需谁确认。
```

### 这一阶段真正完成的定义

只有当你能回答下面 5 个问题，才算这个案例真正进入可发布状态：

1. 哪些 requirement 已前后端闭环；
2. 哪些 requirement 还缺证据；
3. 权限、租户、主数据、导出这 4 类高风险点是否都有验证；
4. PR 是否只包含本次 change 的范围；
5. 当前结论到底是“具备上线评审条件 / 不具备上线评审条件 / 部分达标”中的哪一种。

---

## 11. 为什么这个案例比简单待办案例更适合实战

因为它更贴近企业真实功能：

1. 有列表查询；
2. 有复杂筛选；
3. 有新增/修改表单；
4. 有导出；
5. 有 RP 输入；
6. 有权限、租户、导出、字典、主数据等历史依赖；
7. 更能体现为什么要先 `explore`，为什么要先提炼规则基线。

---

## 12. 结论

如果你的目标是“实战”，那最合理的方式不是一直围绕抽象的简单待办案例讨论，而是拿这种更像真实后台业务模块的功能来驱动流程。

这个“项目管理模块”案例可以作为你后续培训和落地时的主案例，因为它能同时覆盖：

1. 棕地探索；
2. 规则提炼；
3. OpenSpec；
4. Superpowers；
5. 前后端实现；
6. Git/PR/Merge；
7. 发布与归档。

但最后仍要强调：

1. 本案例主要是完整流程主案例；
2. 它默认更适合 `L / High Risk` 讲解和试点；
3. 真正落地时，应先按治理手册做分流，再决定是否需要达到本案例的完整流程强度。
