> 评审日期：2026-03-30  
> 评审范围：`practical-ai-programming` 仓库全部 21 份正式文档（`core/` 5 份、`execution/` 11 份、`review/` 2 份、`history/` 2 份）及 `README.md`  
> 评审视角：以 AI 编程自动化在企业棕地项目中实际落地推广为标准，从方法论完整性、实操可落地性、团队可推广性、风险控制能力四个维度进行评审

## 二、核心优势（应予保留和强化的部分）

### 2.1 棕地项目定位精准且一以贯之

这是本方案最核心的竞争力。目前市面上绝大多数 AI 编程方案都是面向绿地项目（新项目）的演示，而本方案自始至终围绕：

1. 历史系统里如何让 AI "先理解约束、再参与实现"
2. 如何避免 AI 按通用最佳实践"乱改"旧系统
3. 如何在前后端都有历史包袱的情况下做增量扩展

这一定位在实际企业推广中具有极高的实用价值，因为企业 80% 以上的研发工作都是在棕地项目上进行的。

### 2.2 "AI 不能自证完成"的核心纪律

全套文档反复强调且从未妥协的核心纪律：

1. "我本地测过了"不算完成
2. "AI 说通过了"不算完成
3. "看起来没问题"不算完成
4. 必须有结构化证据、人工审批、验收矩阵

这条纪律是将 AI 编程从"Demo 级别"推进到"企业工程级别"的关键分水岭。建议在推广中将此作为团队铁律，不可动摇。

### 2.3 三条治理路径的分流设计

`S-Low` / `M-Medium` / `L-High Risk` 三条路径的设计非常务实：

1. 避免了"所有需求一刀切走重流程"的推广阻力
2. 四维度判断（工作量、风险等级、影响面、不确定性）比简单 T-Shirt Size 更严谨
3. 硬性升级条件（权限、租户、导出语义等）防止了"工作量小就走轻流程"的误判
4. `M-Medium` 快车道照顾了团队中最高频的需求形态

### 2.4 规则基线治理机制

将 `.cursor/rules/*.mdc` 视为"项目基础设施"而不是"每次需求的临时产物"，这一治理思路非常正确。Owner 制度、更新触发条件、一线反馈机制（`rule conflict / rule gap / rule outdated`）形成了可持续运转的治理闭环。

### 2.5 工具前置与 Fallback 机制

`AI-WORKFLOW-TOOLING-PREREQUISITES.md` 是一份极有价值的文档。它正面回答了一个很多 AI 方案刻意回避的问题："如果工具不可用怎么办？"三级环境判断（理想/半可用/受限）和每个 `/opsx-*` 命令的人工 fallback 方案，确保了方法论不会因为工具依赖而变成空中楼阁。

### 2.6 需求变更回写流程

`BROWNFIELD-CHANGE-UPDATE-WORKFLOW.md` 解决了一个实战中极其常见的问题：开发过程中发现需求遗漏后应该怎么办。"先更新 change，再继续开发"的纪律，以及四类变化的分类处理方式（新 requirement / requirement 细化 / 设计变更 / 任务补充），体现了很强的工程实战经验。

## 三、需要改进的问题（按优先级排列）

### 3.1 【高优先级】文档间交叉引用过密，新人认知负荷偏高

**问题描述：**

当前 21 份文档之间的交叉引用非常密集。几乎每份文档都会推荐"先补看"或"建议连读"另外 3-5 份文档。虽然单独看每份文档的引用都是合理的，但从新人视角来看，整体阅读体验容易产生"到底先看哪份"的迷茫。

**具体表现：**

1. `README.md` 推荐先看 7 份文档
2. `AI-ADOPTION-DOCUMENT-CATALOG.md` 推荐连读 5 份
3. `AI-ADOPTION-GOVERNANCE-HANDBOOK.md` 推荐连读 5 份
4. `BROWNFIELD-AI-DEVELOPMENT-INDEX.md` 推荐连读 6 份
5. 多份文档的推荐阅读序列存在重叠但顺序不完全一致

**影响：**

1. 团队新人容易"还没开始做事就被文档量压住"
2. 不同文档给出的阅读路径有微妙差异，可能导致理解分歧
3. 推广时的培训成本偏高

**改进建议：**

1. 建立一份不超过 1 页的 **"团队推广单页速查卡"**（One-Pager），只列最核心的 3 个角色各自应读的 3 份文档
2. 统一所有文档的"推荐连读"部分，确保给出的阅读序列完全一致
3. 考虑在 `README.md` 中增加一个可视化的阅读路径图（Mermaid flowchart），比文字列表更直观

### 3.2 【高优先级】缺乏"团队推广落地度量机制"

**问题描述：**

当前体系非常完整地定义了"做什么"和"怎么做"，但缺少"做得好不好怎么衡量"的度量机制。当团队推广一段时间后，管理者需要回答：

1. 这套方法到底有没有提效？
2. 哪些环节执行得好、哪些被跳过了？
3. AI 辅助的需求和非 AI 辅助的需求相比，质量和效率差异如何？

**改进建议：**

增加一份 **"AI 编程落地效果度量指南"**，至少覆盖：

1. **流程遵从度指标**：各级别需求实际走了对应路径的比例
2. **证据完整度指标**：PR 中结构化证据块的填写率
3. **规则基线健康度**：rules 更新频率、反馈处理速度
4. **缺陷密度对比**：AI 辅助开发 vs 非 AI 辅助开发的上线后缺陷率
5. **验收矩阵闭环率**：requirement 从"未开始"到"验证通过"的平均周期

### 3.3 【高优先级】路径引用中 `knowledge/` 前缀与实际目录结构不一致

**问题描述：**

`README.md` 及所有文档中引用路径均使用 `core/...`、`execution/...` 等形式，但实际仓库目录结构中不存在 `knowledge/` 这一级目录。实际文件直接位于 `core/`、`execution/`、`review/`、`history/` 下。

**影响：**

1. 团队成员按文档中的路径查找文件时会找不到
2. 如果将来自动化工具需要解析路径，会直接报错
3. 影响文档的专业性和可信度

**改进建议：**

二选一：
1. **方案 A（推荐）**：创建 `knowledge/` 目录，将 `core/`、`execution/`、`review/`、`history/` 移动到其下，使实际结构与文档引用一致
2. **方案 B**：全局替换所有文档中的 `knowledge/` 前缀，使引用路径与实际目录对齐

### 3.4 【中优先级】缺少"团队技能前置要求"说明

**问题描述：**

当前体系假设团队成员已经具备一定的 AI 编程协作基础。但实际推广中，很多团队成员可能：

1. 从未使用过 Cursor 或类似 AI IDE
2. 不了解 `.cursor/rules` 的工作机制
3. 不理解"提示词工程"的基本原理
4. 不清楚 OpenSpec 的基本概念

**改进建议：**

在 `core/TEAM-ADOPTION-QUICKSTART.md` 中增加一节 **"团队技能前置清单"**，明确：

1. 团队成员需要掌握的最小 AI 编程协作技能
2. 推荐的上手培训路径（例如先用 Cursor 完成 3 个 S-Low 级别的真实需求）
3. 不同角色（TL、后端、前端、测试）各自需要的前置知识

### 3.5 【中优先级】`M-Medium` 快车道的审批时效缺少建议

**问题描述：**

`M-Medium` 快车道的设计很好，但在审批环节缺少时效建议。如果 TL 审批 `proposal/spec/design/tasks` 需要等 2 天，那"快车道"就名存实亡。

**改进建议：**

在治理手册中明确：

1. `M-Medium` 审批建议在 **4 小时内** 完成（或约定一个团队认可的 SLA）
2. 如果超时未审批，开发者可以按"条件性开始"（conditional start）先推进低风险部分
3. 审批不通过时，建议的最大修改-再审轮次（避免无限循环）

### 3.6 【中优先级】缺少失败案例或反面教材

**问题描述：**

当前体系的案例全部是正向的（"应该怎么做"）。但在实际培训和推广中，反面案例往往比正面案例更有教育效果。

**改进建议：**

在 `execution/PROJECT-MANAGEMENT-BROWNFIELD-PRACTICAL-CASE.md` 中增加一节 **"常见踩坑案例"**，例如：

1. **踩坑 1**：AI 跳过探索直接生成代码，导致与旧系统权限模型不兼容
2. **踩坑 2**：只审了 `design.md` 就开工，导致 requirement 遗漏
3. **踩坑 3**：导出功能只测了 happy path，上线后发现筛选条件未传递
4. **踩坑 4**：规则基线半年未更新，AI 按过时的接口规范生成代码

### 3.7 【中优先级】OpenSpec 主案例包缺失

**问题描述：**

多份文档反复引用 `openspec/changes/project-management/` 目录下的示例文件（`proposal.md`、`spec.md`、`design.md`、`tasks.md`），以及 `.cursor/rules/*.mdc` 规则文件。但当前仓库中实际不存在这些文件。

**影响：**

1. 读者无法对照真实示例理解方法论
2. 评审包中的"OpenSpec 主案例包"无法交付
3. 方法论缺乏"最后一公里"的落地示范

**改进建议：**

1. 优先补充 `openspec/changes/project-management/` 下的 4 份示例文件
2. 补充 `.cursor/rules/` 下的 3 份规则基线文件
3. 这些示例不需要和真实业务完全对应，但必须体现方法论中强调的关键要素（兼容性场景、证据块、fallback 标注等）

### 3.8 【低优先级】部分文档存在章节编号跳跃

**问题描述：**

`BROWNFIELD-QUICKSTART-CHECKLIST.md` 中章节编号从 12 直接跳到 14（缺少第 13 步），可能是编辑过程中的遗漏。

**改进建议：**

补充缺失的第 13 步或重新编号。

### 3.9 【低优先级】交付模板的"最小可用填写示例"可以进一步增强

**问题描述：**

`BROWNFIELD-DELIVERY-TEMPLATE.md` 中的最小填写示例已经很好，但部分关键字段（如"工具环境与执行方式"）的填写值是"待确认"。对于第一次使用模板的人来说，如果所有可选值都是"待确认"，他可能不知道"确认后应该填什么"。

**改进建议：**

再补一个"已确认版"的填写示例，展示当工具环境确认后、验证完成后、发布完成后各字段应该是什么样子。

## 四、文档体系结构评审

### 4.1 四层结构评价

| 层 | 定位 | 评价 |
|---|---|---|
| `core/` | 治理、导航、全量目录 | 职责清晰，5 份文档各有定位，无明显冗余 |
| `execution/` | 方法论、执行、案例、验收、交付 | 最厚重的一层，11 份文档覆盖全生命周期，但部分文档之间的边界可以更锐利 |
| `review/` | 评审、结论 | 精简且到位，专家评审包清单和最终结论纪要都很专业 |
| `history/` | 历史归档 | 处理方式正确，讨论稿归档后有明确的"已被哪份正式文档吸收"说明 |

### 4.2 文档间关系清晰度

**做得好的：**
1. `AI-ADOPTION-GOVERNANCE-HANDBOOK.md` 与其他文档的关系边界定义最为清晰
2. "它解决什么 / 它不替代什么"的写法值得所有文档学习
3. 历史文档的归档处理（标注"已被哪份正式文档吸收"）非常专业

**需要改善的：**
1. `BROWNFIELD-AI-PROMPT-HANDBOOK.md` 与 `PROJECT-MANAGEMENT-BROWNFIELD-EXECUTION-PROMPTS.md` 之间存在部分内容重叠（两份都有探索、澄清、OpenSpec 阶段的提示词）
2. 建议明确定位：前者是"通用模板库"，后者是"特定案例的完整执行脚本"，并在两份文档中交叉引用时说清楚

## 五、按角色的推广可行性评估

### 5.1 技术负责人 / 架构师

**可行性：高**

治理手册、方法论总文档、规则基线治理机制对这个角色有很强的吸引力。建议 TL/架构师最先接触这套体系。

**潜在阻力：**
- 审批快车道的实际时间成本可能被低估
- 规则基线的初始提炼工作量可能被低估

### 5.2 一线后端开发

**可行性：中高**

提示词手册、执行手册、规则基线的价值对后端开发者是直接可感知的。

**潜在阻力：**
- 需要从"直接写代码"转变为"先探索、再约束、再实现"，初期体感会慢
- 结构化证据的撰写会被部分开发者视为"额外负担"

### 5.3 一线前端开发

**可行性：中高**

前端相关的提示词和规则约束已经覆盖路由、组件、API 封装、样式体系，实用性好。

**潜在阻力：**
- 前端更新迭代快，部分前端特有场景（SSR、微前端、组件库版本升级）在当前体系中未展开

### 5.4 测试 / 验收负责人

**可行性：高**

验收矩阵 + 交付模板 + 证据门禁对测试和验收角色是直接赋能的工具。

**潜在阻力：**
- 需要测试人员理解 OpenSpec 的 requirement/scenario 结构

### 5.5 项目管理 / 产品经理

**可行性：中**

当前体系主要面向技术团队，产品侧的参与点（需求澄清、验收确认）虽然被提到，但没有专门面向产品经理的文档。

**改进建议：**
- 可以在 `core/TEAM-ADOPTION-QUICKSTART.md` 中增加"产品经理视角的参与节点"

## 六、与行业主流方案的对比优势

| 对比维度 | 本方案 | 行业常见方案 |
|---|---|---|
| 项目类型定位 | 明确面向棕地项目 | 多数面向绿地项目 / Demo |
| AI 能力边界约束 | 全程强约束（不能自证完成、证据门禁） | 多数只提"AI 辅助"但不给约束 |
| 流程分级 | S/M/L 三级 + 硬性升级条件 | 多数一刀切 |
| 规则治理 | 有 owner、更新触发、反馈机制 | 多数"写一次就不管了" |
| 工具降级方案 | 每个工具都有人工 fallback | 多数只讲理想路径 |
| 需求变更处理 | 有正式回写流程 | 多数"直接改代码" |
| 案例复杂度 | 企业级（CRUD + 导出 + 权限 + 租户 + 主数据） | 多数 Todo / 计算器级别 |

## 七、推广落地建议路径

基于评审结论，建议按以下顺序推广：

### Phase 0：文档整备（推广前必做）

1. 修复路径引用不一致问题（`knowledge/` 前缀）
2. 补充 `openspec/changes/project-management/` 示例文件
3. 补充 `.cursor/rules/*.mdc` 规则基线文件
4. 统一所有文档的"推荐连读"序列
5. 制作一页纸速查卡

### Phase 1：核心团队共识（1-2 周）

1. TL / 架构师先完整读完 core 层 5 份文档
2. 团队全员读 `TEAM-ADOPTION-QUICKSTART.md` + `AI-ADOPTION-GOVERNANCE-HANDBOOK.md`
3. 达成"三条路径、规则是基础设施、AI 不能自证完成"的基本共识

### Phase 2：M 级试点（2-4 个需求）

1. 挑选 2-4 个边界清晰的中型需求
2. 按 M-Medium 快车道走完全流程
3. 收集试点反馈，重点观察：审批成本、证据负担、AI 输出质量、团队接受度

### Phase 3：L 级试点（1-2 个需求）

1. 挑选 1-2 个涉及权限/租户/导出的高风险需求
2. 按完整流程走到底
3. 验证完整体系在高复杂度场景下的可操作性

### Phase 4：全面推广 + 度量

1. 建立度量机制
2. 按度量结果持续优化规则基线和提示词资产
3. 每季度复盘一次方法体系有效性

## 八、总结

### 8.1 核心结论

这套方案在以下三个关键点上做到了行业领先水平：

1. **棕地项目约束意识**：全套资料从未偏离"先理解现状、再增量扩展"的核心纪律
2. **AI 行为约束体系**：规则基线 + 证据门禁 + 分流治理 + 需求回写 形成了多层防护
3. **工程闭环意识**："完成"不等于"代码写完"，而是验收矩阵 + 交付模板 + PR + 发布清单全部闭环

### 8.2 最大风险

推广落地时最大的风险不是方法论本身，而是：

1. **团队认知门槛**：文档量大、交叉引用多，可能在推广初期产生抗拒
2. **证据负担感**：结构化证据的撰写对开发者是新增工作，初期需要平衡效率和质量
3. **规则基线的初始投入**：第一次巡查和提炼规则基线的工作量不可低估

### 8.3 最终建议

> 建议在完成 Phase 0 的文档整备后，以 M-Medium 快车道作为推广切入点，用 2-4 个真实需求完成试点验证。成功后再逐步推广到 L/High Risk 场景。全过程中始终坚守"AI 不能自证完成"的核心纪律不动摇。
