# 环节 1：棕地探索提示词

> 来源：`execution/BROWNFIELD-AI-PROMPT-HANDBOOK.md` 第 4.1 节  
> 使用时机：分流判断为 M-Medium 后，进入最小探索

## 实际使用的提示词

```text
请先进入棕地项目探索模式，不要设计新功能，也不要写代码。我要在这个历史项目中新增"设备管理"模块，功能包括：
1. 列表查询
2. 新增
3. 修改

请重点找出：
1. 相关前端入口页面、组件、路由和 API 调用位置
2. 相关后端 Controller、Service、Repository、数据库表
3. 已有功能能力和缺口
4. 兼容性风险和可能影响的旧链路
5. 需要进一步向业务确认的问题

特别关注：
6. 系统里是否有相近的管理模块（如合同管理、客户管理），我可以参考它们的实现模式
7. 前端有哪些共享组件（查询表单、表格、弹窗、导出按钮），它们有没有特殊行为或已知坑
8. 后端的统一返回体、异常处理、租户机制、字典服务、导出工具分别是什么
9. 列表接口返回的状态字段是后端翻译还是前端翻译

要求：
1. 优先基于现有代码和文档总结
2. 不要假设这是绿地项目
3. 对不确定内容明确标注"待确认"
4. 每条关键结论至少附一个真实文件路径
5. 至少给出一条调用链或页面到接口链
6. 输出按"前端 / 后端 / 数据 / QUIRK / 待确认问题"分组
```

## 与方法论原版的差异

原版提示词（手册 4.1 节）输出分组是"前端 / 后端 / 数据 / 风险 / 待确认问题"。实操中增加了：
- 第 6-9 条特别关注项（根据 M 级需求的实际需要增加）
- 输出分组增加了"QUIRK"一类（碰撞点 #3 的发现）
- 增加了"列表接口返回的状态字段是后端翻译还是前端翻译"这一条（碰撞点 #8 的前置预防）

## 实际效果

AI 正确输出了：
- 合同模块的完整 Controller → Service → ServiceImpl 调用链
- 5 个 QUIRK（SearchForm 重置行为、BaseTable pageSize 默认值、FormDialog confirm 行为、ExportButton 参数传递、DictService key 类型）
- 字段翻译约定：后端不翻译，前端用 DictService 本地翻译

## 碰撞发现

- 🔴 碰撞点 #2：M 级中巡查/提炼/固化三步拆得太细。探索完自然就知道规则了，不需要单独一步"提炼"。
- 🔴 碰撞点 #3：QUIRK 不在方法论的产出物清单里。如果提示词不加"QUIRK"分组，AI 不会主动聚焦这类信息。
