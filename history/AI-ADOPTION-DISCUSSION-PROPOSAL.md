# AI 编程落地分流治理方案讨论稿

> 当前状态：历史讨论稿，已归档到 `knowledge/history/`，不作为当前正式治理口径。  
> 正式口径请优先参考：`knowledge/core/AI-ADOPTION-GOVERNANCE-HANDBOOK.md`、`knowledge/review/AI-ADOPTION-FINAL-CONCLUSION-MINUTES.md`

> 文档性质：内部讨论稿，不是最终制度文件。  
> 目标：在不推翻现有 `OpenSpec + Superpowers + 棕地规则基线` 体系的前提下，解决“流程过重、认知负荷前移、规则维护成本高”三个真实推广问题。  
> 适用范围：面向本团队在棕地项目中的 AI 编程落地，不覆盖所有项目类型，也不替代现有研发管理制度。

---

## 1. 背景

我们现有资料已经形成一套较完整的棕地项目 AI 开发体系，核心价值体现在：

1. 强调棕地项目约束，而不是绿地演示；
2. 用 `OpenSpec` 约束需求、设计与任务；
3. 用规则基线约束 AI 不要自由发挥；
4. 用验收矩阵、交付模板和验证门禁阻断“AI 自证完成”。

外部专家评审后，整体结论是正向的，但也指出了三类必须正视的问题：

1. 一刀切流程容易引发“流程过重”的推广阻力；
2. AI 编程把更多思考责任前移给人，团队能力结构会被重新要求；
3. 规则基线如果没有治理机制，后续容易失效或腐化。

本讨论稿的目标不是否定现有体系，而是在现有体系上增加一层更适合企业推广的“分流治理层”。

---

## 2. 当前问题

## 2.1 流程过重

如果一个简单需求也要求完整走探索、proposal、design、tasks、验收矩阵、交付模板，团队会把这套方法理解成“为了 AI 而 AI”。

真实风险不是流程本身，而是：

1. 小需求滥用重流程；
2. 团队把流程视为教条；
3. 最终导致流程被绕开，而不是被尊重。

## 2.2 认知负荷前移

AI 并没有消灭思考，而是把大量低价值编码劳动替换成了更高要求的设计、约束、审批和验证劳动。

这意味着：

1. 开发者需要更清楚地表达范围与边界；
2. TL / 架构师要承担更多规则和方案审批责任；
3. 团队不能再把“会写代码”当作唯一核心能力。

## 2.3 规则基线维护风险

`.cursor/rules/*.mdc` 已经被证明是有效的，但如果没有 owner、触发条件和维护机制，就会变成：

1. 文档存在但没人更新；
2. 内容过时但仍被 AI 继续引用；
3. 一线开发发现冲突也不知道如何反馈。

---

## 3. 本次方案目标

本次优化只解决四件事：

1. 给现有流程增加分级路由，避免一刀切；
2. 把规则基线改造成“静默生效、受控升级”的基础设施；
3. 给最常见的中型需求建立高频、低摩擦的快车道；
4. 把“机器证据优先”落成更可执行的门禁机制。

本次方案不做：

1. 推翻现有 OpenSpec 体系；
2. 否定现有文档资产；
3. 承诺 AI 可以自动完成真实业务开发；
4. 取代人工评审、上线审批和业务验收。

---

## 4. 核心决策

## 4.1 决策一：按“工作量 + 风险”双轴分流

不再采用所有需求一刀切流程，也不只按预计工时做简单 T-Shirt Size。

新的路由原则：

1. 先看工作量：`S / M / L`
2. 再看风险：`Low / Medium / High`
3. 最终由两者共同决定走哪条流程

这样可以避免：

1. 小工作量但高风险的改动被错误地走轻流程；
2. 工作量中等但边界清晰的需求被迫走最重流程。

## 4.2 决策二：规则基线默认静默生效

`.cursor/rules/*.mdc` 视为项目基础设施，而不是每个需求都要重新提炼的“任务产物”。

执行口径：

1. 一线开发默认消费 rules；
2. TL / 架构师集中维护 rules；
3. 一线开发在发现冲突时可发起更新请求；
4. 规则更新通过专门 PR 和 review 落地。

## 4.3 决策三：为 M 级需求建立审批快车道

M 级需求是最常见的业务开发形态，必须有一条：

1. 比完整流程轻；
2. 比直接开干稳；
3. 能让团队愿意长期使用

的标准路径。

## 4.4 决策四：机器证据优先，人工最终裁决

今后不再接受：

1. “我本地测过了”
2. “应该没问题”
3. “AI 说已经完成了”

作为完成依据。

但也不能把门禁简化成“贴一段日志”。  
正确做法是：

1. 用结构化机器证据证明执行过；
2. 用人类 reviewer 判断这些证据是否足够支撑当前结论。

---

## 5. 分流标准（建议稿）

## 5.1 `S-Low`：微小且低风险

典型场景：

1. 单一字段展示；
2. 文案调整；
3. 样式微调；
4. 范围非常清晰的简单 bug。

建议流程：

1. 直接开发；
2. 默认应用现有 `.cursor/rules`；
3. 跳过 OpenSpec；
4. PR 中附最小机器证据。

不允许进入 `S-Low` 的情况：

1. 改权限；
2. 改租户逻辑；
3. 改导出语义；
4. 改旧接口返回结构；
5. 改事务边界；
6. 涉及高不确定历史逻辑。

## 5.2 `M-Medium`：中型且风险可控

典型场景：

1. 标准单表/双表 CRUD；
2. 独立页面新增；
3. 标准第三方 API 对接；
4. 边界清晰的功能增强。

建议流程：

1. 最小探索；
2. 使用 `@openspec-ff-change` 生成 `proposal/spec/design/tasks`；
3. 人工快速审批；
4. 审批通过后开发；
5. 必须补验收矩阵；
6. 必须提交结构化机器证据。

人工审批最少覆盖：

1. proposal 范围与非目标；
2. spec 的 requirement / scenario；
3. design 的接口、字段、复用边界；
4. tasks 的验证项是否完整。

## 5.3 `L` 或 `High Risk`

典型场景：

1. 多租户；
2. 权限体系改造；
3. 核心历史资产调整；
4. 跨多个服务或模块联动；
5. 高不确定性需求。

建议流程：

1. 完整探索；
2. 校对现有规则基线；
3. 完整 OpenSpec；
4. 完整实施计划；
5. 多角色执行；
6. 完整验收矩阵与交付模板；
7. 发布前完整验证门禁。

---

## 6. 角色职责

## 6.1 一线开发

主要职责：

1. 按分流标准选择正确流程；
2. 在现有规则基线下使用 AI；
3. 对 M/L 级需求补齐必要 artifacts 和证据；
4. 如果发现 rules 与实际项目冲突，发起更新请求。

不承担的职责：

1. 每次需求都重新提炼项目级规则；
2. 单独决定高风险需求是否可以走轻流程；
3. 用主观口头说明替代验证证据。

## 6.2 Tech Lead / 架构师

主要职责：

1. 维护 `.cursor/rules/*.mdc`；
2. 审批 M/L 级需求的范围、边界和设计；
3. 决定存在争议时的流程分级；
4. 在复盘后沉淀新规则。

## 6.3 Reviewer

主要职责：

1. 看 PR 是否与 change 范围一致；
2. 看机器证据是否真实、足够；
3. 看是否存在兼容性遗漏；
4. 没有足够证据时直接 reject。

## 6.4 发布负责人 / 验收负责人

主要职责：

1. 检查验收矩阵；
2. 检查交付模板与发布清单；
3. 做最终发布评审；
4. 确认当前是否具备进入发布评审条件。

---

## 7. M 级需求快车道 SOP

建议标准起手话术：

```text
这是一个 M 级需求。请先基于当前项目规则基线做最小探索，再使用 `@openspec-ff-change` 生成 `proposal/spec/design/tasks`。生成后停下，等待我审批。
```

审批动作固定为 4 步：

1. 看 proposal 范围是否正确；
2. 看 spec 是否漏 requirement / scenario；
3. 看 design 的接口、字段、复用边界是否合理；
4. 看 tasks 是否包含验证与回归项。

审批通过后再开发。  
如果审批时发现：

1. 需求边界不清；
2. 字段契约不清；
3. 主数据来源不清；
4. 验证项明显缺失；

则退回 AI 重新生成，而不是带着有缺口的 design 直接开工。

---

## 8. 规则基线治理机制（建议稿）

## 8.1 规则所有权

建议 owner：

1. 项目级规则：TL / 架构师
2. 后端规则：后端负责人
3. 前端规则：前端负责人

## 8.2 更新触发条件

以下情况触发规则评估：

1. 高风险需求结束后；
2. 团队多次重复踩同一类坑；
3. 历史项目模式发生稳定变化；
4. 现有 rules 与真实项目冲突。

## 8.3 更新方式

建议：

1. 单独 PR；
2. 写明更新原因；
3. 写明影响范围；
4. 必要时同步更新 prompt handbook / checklist。

## 8.4 一线开发反馈机制

允许一线开发提交：

1. rule conflict
2. rule gap
3. rule outdated

但不建议在日常需求分支中直接随手改规则。

---

## 9. 结构化机器证据门禁

推荐统一采用如下最小格式：

```md
## Verification Evidence

### Command
- 

### Environment
- 

### Result
- 

### Evidence Location
- 

### Conclusion
- 

### Residual Risk
- 
```

门禁原则：

1. 没有机器证据，不进入“已完成”；
2. 有机器证据，但不能证明关键风险，也不进入“具备发布评审条件”；
3. 机器证据证明执行过，人类 reviewer 负责判断是否充分。

---

## 10. 推广顺序

建议不要全团队一次性推开，而是分阶段落地。

## Phase 1：先建立共识

目标：

1. 团队理解为什么要分流；
2. 团队理解 rules 是基础设施；
3. 团队理解“AI 不能自证完成”。

## Phase 2：先试点 M 级快车道

目标：

1. 在 1-2 个中型需求上试运行；
2. 观察审批成本、开发体验和证据门禁效果；
3. 不急着一开始就全量推 L 级完整流程。

## Phase 3：再推广到高风险需求

目标：

1. 在多租户、权限、导出、跨模块场景中正式启用完整流程；
2. 复盘后更新 rules 和 prompt 资产。

---

## 11. 试点方案建议

建议挑一个具备以下特征的需求做试点：

1. 不是太小，否则看不出流程价值；
2. 不是最高风险，否则团队一开始压力过大；
3. 具备页面、接口、验证、PR 全链路；
4. 最好是标准后台业务能力。

最适合的试点类型：

1. 标准 CRUD 模块；
2. 单模块页面新增；
3. 标准导出或查询增强；
4. 单一第三方 API 对接。

不建议作为首批试点：

1. 权限体系改造；
2. 多租户逻辑重构；
3. 核心账务、清分、资金结算类场景。

---

## 12. 风险与应对

## 12.1 风险：团队仍觉得流程重

应对：

1. 先落地分流；
2. 用 M 级快车道证明效率；
3. 不要让 S 级需求滥用 OpenSpec。

## 12.2 风险：rules 失效

应对：

1. 建 owner；
2. 建更新触发条件；
3. 建专门 PR 机制；
4. 定期复盘。

## 12.3 风险：AI 草案质量不稳定

应对：

1. M 级需求审批时必须 review proposal/spec/design/tasks；
2. 不允许只看 design 就开干；
3. 对字段契约、主数据来源、兼容场景重点审查。

## 12.4 风险：证据门禁流于形式

应对：

1. 用结构化证据块；
2. 明确 Reviewer 不是看“有没有日志”，而是看“日志证明了什么”；
3. 验收矩阵与交付模板联动。

---

## 13. 建议下一步

如果团队认可本讨论稿，下一步建议按这个顺序落地：

1. 先把分流标准定稿；
2. 再把角色职责定稿；
3. 再为 M 级需求写标准 SOP；
4. 最后把机器证据模板接入现有验收与交付文档。

在此之前，不建议直接大改现有全部资料。

---

## 14. 一句话总结

> 这次优化的核心，不是把重流程废掉，而是把它准确地用在真正高风险的变更上；让 rules 静默生效，让 M 级需求高频顺滑，让证据门禁真正替代“口头完成”。
